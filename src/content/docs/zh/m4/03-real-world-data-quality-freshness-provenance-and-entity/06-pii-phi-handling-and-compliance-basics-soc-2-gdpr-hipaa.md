**一句话：** 个人信息和健康数据必须做到最小化、受到保护，并遵守法律对存储、写入日志、发送给模型 API 的限制；FDE 需要对 SOC 2、GDPR 和 HIPAA 有基本的了解，才能在医疗和金融项目中安全地开展工作。

## 是什么

**PII** 是能识别出某个人的数据；**PHI** 是健康数据（要求更严格的子集）；金融数据同样敏感。负责任地处理这类数据，要做到：**最小化**（只传输必要的部分）；在不需要完整值的地方，用**掩码**或**用 token 替换敏感值**（tokenization）；对传输中和静态存储的数据做**加密**；严格控制访问权限；并且清楚数据会流向哪里，尤其不能把它泄露到日志里，也不能把它发给条款允许训练或留存数据的模型 API。这几个框架在性质上各不相同：**SOC 2** 是 AICPA 对你的安全控制措施做的*自愿*审计或鉴证（不是法律，但企业客户常会提出这个要求）；**GDPR** 是欧盟关于个人信息的权利与义务，包括合法性基础、删除，以及通过充分性认定或标准合同条款（SCC）把数据*传输*出欧盟的规则（注意：GDPR **并不**要求数据在物理上留在欧盟）；**HIPAA** 针对美国的健康数据，要求采取保护措施，并与任何接触 PHI 的一方（包括模型供应商）签订业务伙伴协议（BAA）。

## FDE 为什么需要

在医疗和金融领域，合规是必须通过的 gate：医院不会部署一个接触 PHI、却没有 HIPAA 保护措施和 BAA 的功能；欧盟客户期望你符合 GDPR；安全审查往往从一句“把你们的 SOC 2 发给我们”开始。把受监管的数据发到不合规的端点，或者把它写进日志，是事故，而不是 bug。具备基本的认识，你才能设计出在这些领域真正能上线的东西。

## 核心概念

- **最小化：** 只发送任务需要的字段；别因为“以防万一”就把整条记录搬走。
- **掩码或用 token 替换，并加密：** 降低可识别性；保护传输中和静态存储的数据。
- **别泄露到日志或提示词里：** 写日志或发给模型之前，先对 PII/PHI 脱敏。
- **模型供应商的条款：** 发送受监管的数据之前，先确认对方不做训练或留存（或使用合规的服务档位）；PHI 要签 BAA。
- **SOC 2 / GDPR / HIPAA：** 知道哪个适用，以及它们的核心要求（自愿的控制措施鉴证 / 数据主体权利 + 传输规则 / PHI 保护措施 + BAA）。

## 常见误区

- **“把数据发给 LLM，和调用任何其他 API 没区别。”** 数据可能因此离开你的信任边界；先查条款，并先最小化或掩码；PHI 需要 BAA。
- **“合规是法务的事。”** 许多要求其实是需要你来实现的工程控制措施：访问控制、加密、日志、留存。
- **“供应商合规，我们就合规。”** 合规是责任共担的；你的应用必须落实自己那一份，并签好相应的协议（BAA/DPA）。

## 典型面试题

<details>
<summary>医院希望你的 AI 功能处理患者数据，会涉及哪些合规问题？</summary>

这是 HIPAA 下的 PHI，所以需要保护措施、访问控制、加密、审计日志、最小化，并且要与每一个接触它的子处理者签订业务伙伴协议，包括模型供应商，对方必须提供可用于 HIPAA 场景的服务（HIPAA-eligible）。在发送任何 PHI 之前，我会先确认 BAA 已经就位。

</details>

<details>
<summary>把客户数据发给模型 API 之前，你最少要检查什么？</summary>

我会确认：发送的是不是必需的最少数据（做了最小化，能掩码的已经掩码）；有没有 PII/PHI 流向不该去的地方；供应商按其数据条款会怎么处理这些数据，即会不会用输入做训练或留存输入。对任何敏感数据，优先选择不训练、零留存或企业档位的服务，需要时还要有 BAA/DPA。

</details>
