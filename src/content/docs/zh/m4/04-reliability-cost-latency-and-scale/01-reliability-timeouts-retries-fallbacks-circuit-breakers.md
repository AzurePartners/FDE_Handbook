**一句话：** 模型和 API 调用会失败、变慢、被限流，所以生产环境的可靠性来自超时、带退避的重试、降级、熔断器、批处理和缓存，这是在某个依赖挂掉时仍能保持自身可用的标准工具箱。

## 是什么

只依赖单个端点，你的功能就只能和这个端点一样可靠。超时、带退避的重试、幂等性和缓存这些通用的基础组件，已在模块一中讲过（[重试与退避](../../m1/06-reliability-scale/03-retries-and-backoff.md)及相邻页面）；用在模型和 API 调用上，这套工具箱包括：

- **超时：** 限定最多等多久就放弃，这样卡住的调用不会一直挂着。
- **带退避和抖动的重试：** 对暂时性错误（429、503、超时）进行重试，每次等得更久，并加入随机性，这样就不会不停地冲击一个已经吃力的服务。
- **降级：** 主模型或主供应商失败时，切换到备用的模型或供应商，或者进入降级模式。
- **熔断器：** 多次失败后，停止调用并快速失败，同时定期探测，看服务是否恢复。
- **批处理：** 把许多小调用合并成更少的调用，以减少开销，并保持在限额之内。
- **缓存：** 复用最近的结果，而不是重新计算或重新调用。

## FDE 为什么需要

客户评判一个功能，看的是需要时它能不能用，而“供应商宕机了”这个理由在生产环境中说不过去。这些技术把供应商的偶发问题变成用户看不到的小波动。重试必须搭配 **幂等性** 使用，这样被重试的写操作才不会重复扣款或重复发布。

## 核心概念

| 技术 | 应对的问题 |
| --- | --- |
| 超时 | 卡住或很慢的调用 |
| 重试 + 退避/抖动 | 暂时性错误，同时避免惊群效应（thundering herd） |
| 降级 | 主供应商失败 |
| 熔断器 | 持续性宕机；快速失败 |
| 批处理 | 开销与限流 |
| 缓存 | 重复的相同工作与成本 |

## 常见误区

- **“立刻重试，而且要频繁重试。”** 这会让本已过载的供应商雪上加霜；要用退避和抖动，并设上限。
- **“一个供应商就够了。”** 单一依赖就是单点故障；关键路径要有降级方案。
- **“重试总是安全的。”** 只有操作是幂等的才安全；否则重试可能重复产生副作用。

## 典型面试题

<details>
<summary>当模型供应商出问题时，你如何保证功能的可靠性？</summary>

用超时，避免调用一直挂着；对暂时性错误做带指数退避和抖动的重试；准备备用供应商或降级模式；用熔断器在宕机期间快速失败；再用批处理和缓存降低负载和成本。被重试的写操作要做成幂等的，这样就不会重复产生副作用。

</details>

<details>
<summary>盲目重试有什么风险，该如何避免？</summary>

有两个风险：激进的立即重试会给本已吃力的供应商增加负载（惊群效应），而重试非幂等的操作可能让一笔扣款或一条消息重复出现。带抖动并设上限的退避可以解决前者，幂等键可以解决后者。

</details>
