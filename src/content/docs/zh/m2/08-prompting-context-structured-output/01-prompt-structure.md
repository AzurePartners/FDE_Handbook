**一句话：** 提示词结构是一份清单，列出生产环境的提示词要写明的各个部分（角色、目标、上下文、约束、示例、输出格式和拒答条件），让模型在每个请求上都用同样的方式做同样的事。

## 是什么

聊天时的提示词可以只有一行，因为你在场，随时可以澄清。产品里的提示词则要无人值守地处理成千上万条从没见过的输入，而且答案由代码来读，所以它必须像规格说明一样起作用。

打个比方，想想呼叫中心客服手边的那本活页册：用途、事实、规则、示例通话、要填写的表单，还有一张给“哪一类都不属于”的来电准备的升级卡片。没有这张卡片，客服就会即兴编出一个语气笃定的答案。模型也一样。

Anthropic 建议把模型看作“一位才华出众、但刚入职的员工，不了解你们的规范和工作流”。各家供应商对这些部分的命名和排序不尽相同，把它们当作一份检查清单来用即可。

## FDE 为什么需要

一家货运经纪公司的邮件分流试点，根据模型的回答把邮件分到五个队列。提示词是“你是一位物流专家助手。请对这封邮件分类。”日志显示，缺少的每个部分都对应着一种失败，从路由器无法解析的啰嗦回复，到编造的运价。

FDE 把它改写成七个部分，用日志里记录的邮件在两个版本上各重跑一遍，并且仍然在代码里校验标签：提示词只起引导作用，不起强制作用。

## 核心概念

### 七个部分

```text
系统提示词（每次请求都有）
角色：你负责为一家货运经纪公司的运营邮箱分流邮件。
目标：只选一个队列，让对应的团队及时回复。
上下文：每个队列一行说明。货损、短缺或丢失属于 Claims。
约束：绝不回复发件人，因为只有持牌经纪人才能回复。
示例：两封带标签的邮件，其中一封同时涉及货损和账单。
输出格式：JSON，包含 "queue" 和一句话的 "reason"。
拒答条件：与主题无关、无法阅读或询问价格：
  返回 queue "human_review"。
用户消息：邮件正文。
```

| 缺失的部分 | 试点中的失败 |
|---|---|
| 角色 | 语气泛泛，职责范围不断漂移 |
| 目标 | 没人要求的回复草稿 |
| 上下文 | “托盘到货时被压坏”被分到 Billing |
| 约束 | 凭空冒出的“Urgent Billing”标签 |
| 示例 | 标签拼写不一致 |
| 输出格式 | 路由器拒收的啰嗦回复 |
| 拒答条件 | 编造的运价 |

### 系统提示词还是用户消息

常设的部分放进系统提示词，写一次并做版本管理。本次请求的材料（邮件、检索到的文档、问题）放进用户消息，长文档在前，问题在最后；Anthropic 对多文档输入的测试发现，这样做最多可提升 30%。如果把用户文本或文档文本放进系统提示词，它们就会获得 operator 的优先级。

### 把规则当规格说明来写

给每条规则说明理由。在 Anthropic 的例子里，“绝不要使用省略号”的效果不如告诉模型这段回复会交给文字转语音引擎朗读；模型会根据理由推及类似的情形。

说明该做什么，语气要平和。Google 警告，像“不要推断”这样宽泛的否定指令会被过度套用；Anthropic 和 OpenAI 指出，如今“CRITICAL: you MUST”这类措辞往往会让模型过度套用规则。要删掉相互矛盾的规则。

拒答条件就是给模型留的退路：何时拒绝、追问或交接，以及该返回什么，比如“文档里没有答案时返回 not_found”。它们只起引导作用，不能强制执行；OWASP 的 LLM08:2026 指出，授权检查“不得委托给 LLM，无论是通过系统提示词还是其他机制”。

### 推理放在哪里

如果由代码解析回复，“先解释，再回答”就会把解析搞坏；Anthropic 指出，当只在提示词里要求输出 JSON 时，模型常常会先用文字进行推理。可以使用内置的思考功能（按输出计费，常常是隐藏的，所以不能当作审计日志），或者在 schema 里把推理字段放在答案之前，代码只记录它，从不依据它采取行动。

## 常见误区

- **“‘你是世界级专家’能让模型更准确。”** 一项针对 162 种角色设定、2,410 个事实性问题的研究发现，准确率没有提升。角色只设定范围和语气，真正起作用的是其余部分。
- **“提示词越长越好。”** Microsoft 把过长的系统消息列为一个陷阱。测试暴露出失败后，再加规则。
- **“提示词里写了‘拒答薪资问题’，所以应用是安全的。”** 提示词什么都不能保证。任何绝不能发生的事，都需要在代码里加检查。

## 典型面试题

<details>
<summary>生产环境的提示词有哪些部分？为什么要把它们分开列出来？</summary>

角色、目标、上下文、约束、示例、输出格式和拒答条件。分开列出来能暴露缺口：没有输出格式，解析器就会出错；没有拒答条件，模型就会对超范围的问题给出笃定的回答。

</details>

<details>
<summary>哪些内容放进系统提示词，哪些放进用户消息？</summary>

常设的部分放进系统提示词，写一次并做版本管理。本次请求的文档和问题放进用户消息。

</details>

<details>
<summary>讲讲你会怎么设计一个为客服人员起草保修理赔回复、供其审核的提示词。</summary>

一个负责起草的角色；政策和理赔记录作为每次请求的上下文；再加一条规则：“绝不承诺退款，因为只有客服人员才能批准退款。”输出字段为 draft、policy_clause 和 needs_human；涉及人身伤害、法律威胁或不在保修范围内的产品时，就设置 needs_human。然后我用过往的理赔记录来测试。

</details>

<details>
<summary>一位利益相关方想加上一条“CRITICAL: NEVER DISCUSS PRICING”，你怎么办？</summary>

我会把它换成一条平和的规则，附上理由和替代做法：“不要报价，因为价格由销售团队每周制定；请给出定价页面的链接。”全大写的强调语气容易导致规则被过度触发。我会重跑相近的测试用例，如果泄露的代价很高，就再加一道代码检查。

</details>
