**一句话：** 不是所有系统都通过 REST API 交换数据；大量真实的集成工作靠文件投递、直接读数据库或现成的 SaaS 连接器来传数据，每种方式都有自己的格式、负责方和故障点。

## 是什么

很多客户系统比 REST API 出现得还早，或者是批量传输数据的。常见的集成边界有：投递给另一个系统的文件、通过 API 上传的文件、直接读数据库，以及 SaaS 连接器。每种方式的失败方式都不一样。

## FDE 为什么需要

客户常说“把数据从老系统里弄出来就行”，他们指的往往是某个文件夹里的夜间 CSV 导出，而不是 API。一个计费平台可能只提供只读副本。只会调 REST 的 FDE，碰到没有 API 的客户系统就会束手无策。

## 核心概念

### 文件投递：SFTP、CSV 导出、共享文件夹

一个系统按计划把文件（通常是 CSV）写到某个文件夹，这个文件夹通常通过 SFTP（基于 SSH 的文件传输）访问，另一个系统之后再去读取。谁也不调用谁；文件本身就是接口。

- **负责方：** 导出数据的团队，他们控制导出时间和格式。
- **何时出问题：** 文件晚到或根本没到，列名被悄悄改了，或者文件在写入过程中就被读取。
- **检查什么：** 文件是否完整写入，表头是否仍然对得上，以及文件干脆没出现时会发生什么。

### 直接读数据库

有些系统只通过数据库的读权限，或者只读副本来开放数据。只读副本是一份保持同步的实时拷贝，用来让外部查询不拖慢或锁住生产库。

- **负责方：** 数据源团队，他们改一列或一张表时，不一定会通知每个使用方。
- **何时出问题：** 副本落后于主库，schema 变更导致旧查询失效，或者慢查询锁住了共享资源。
- **检查什么：** 你读的是副本还是线上生产库，副本最多可能落后多少，以及 schema 文档在哪里。

### SaaS 连接器

Salesforce、HubSpot、QuickBooks 等很多工具都自带现成的连接器（它们自己的，或者通过 Zapier），不用你自己写底层 API 调用就能搬运数据。

- **负责方：** 供应商，它随时可能改变连接器的行为。
- **何时出问题：** 触发了连接器的限流，字段映射配错了，或者它悄悄丢掉了无法映射的记录。
- **检查什么：** 连接器自己的日志在哪里，它们很少出现在你的应用日志里。

### 通过 API 上传文件

有些 API 接收的是文件而不是 JSON。客户端以 `multipart/form-data` 格式发送，这种请求体被分成多个部分：文件的字节数据，加上普通的表单字段。

```bash
curl -X POST https://api.example.com/v1/invoices/upload \n  -H "Authorization: Bearer $API_KEY" \n  -F "file=@invoice.pdf;type=application/pdf" \n  -F "customer_id=c_123"
```

- **负责方：** 运营接收端 API 的一方，由它设定大小和类型限制。
- **何时出问题：** 文件太大（413），类型不被允许（415），或者解析太慢导致请求超时。
- **检查什么：** 由你接收上传时，拒绝超过大小上限的文件，并检查真实的文件类型，而不只是扩展名。把文件存到对象存储（比如 Amazon S3），数据库里只保存它的 key，并在后台 worker 里解析，这样上传请求能很快返回。

## 常见误区

- **“没有 REST API 就没法集成。”** 文件投递、读数据库和 SaaS 连接器都是标准做法，在成熟企业客户那里往往更常见。
- **“数据库只读副本和生产库是一回事。”** 副本可能比主库落后几秒甚至几分钟，而且是只读的。
- **“SaaS 连接器配置好就能一直正常工作。”** 连接器有自己的配额、失败方式和日志。要把它当作另一个需要监控的系统。

## 典型面试题

<details>
<summary>客户说他们的老计费系统没有 API。你有哪些办法拿到它的数据？</summary>

问清楚它能否定时导出文件（CSV 走 SFTP 很常见），能否拿到它的数据库或只读副本的读权限，或者是否已经有 SaaS 连接器支持它。

</details>

<details>
<summary>一个 SaaS 连接器在某个特定字段上悄悄停止同步新记录。你先查哪里？</summary>

先查连接器自己的日志和字段映射，因为它运行在你的代码之外。它无法映射的字段通常会被直接丢弃，而不是报错。

</details>
