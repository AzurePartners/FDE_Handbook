**一句话：** 交接包是你交给客户的一个文件夹，让客户自己的人在没有你的情况下，也能运行、重启并理解这个系统。

## 是什么

你离开之后，Course Support Assistant（课程支持助手）还会留下来。协调员需要知道怎么启动它、它能读取哪些内容、它宕机时该怎么办，以及它做不了什么。交接包就是用书面形式回答这些问题。

交接包包含哪些内容，见[交接包](../../m5/07-pilot-value-handoff-and-productization/05-the-handoff-package.md)（M5）；如何撰写局限，见[记录已知局限](../../m2/12-safety-guardrails-hitl/09-known-limitations.md)（M2）。本页是实战项目的提交检查清单。

## FDE 为什么需要

如果只有你能运行它，你造出来的就是一个依赖，而不是一个解决方案。一个没有重启流程的系统，第一次文档上传失败时就会变成客户的紧急事故。交接包同时也在保护你：它说明了交付了什么，以及哪些内容不在范围内。

## 核心概念

### 你要交付什么

一个包含以下内容的文件夹，每一项都是一个简短的文件。

| 项目 | 内容 | 完成标准 |
|---|---|---|
| 操作指南 | 日常使用、输入与输出、如何更新课程文档、联系谁 | 协调员无需帮助就能照着操作 |
| 安装说明 | 环境、版本、重新安装的步骤 | 在一台全新的机器上能跑通一次运行 |
| 权限 | 系统会访问哪些账户、密钥和数据，是读还是写 | 文件中没有出现任何密钥 |
| 兜底与重启 | 常见故障及修复方法（runbook），服务宕机时该怎么办 | 每种故障都有第一步动作 |
| 已知局限 | 用用户语言写的清单，附绕过办法 | 与候选发布版本一致 |
| 运行证据 | 评测表、代理用户测试记录、运行日志样例 | 文件都能打开，且与声明的版本一致 |
| 版本记录 | 提示词、数据快照、模型、配置 | 与 rc 标签一致 |

### 通过标准

- 一位没有参与项目的评审人，仅凭书面说明就完成了安装和一次完整运行。
- 重启和兜底步骤至少测试过一次，并记录了结果。
- 权限表按名称和用途列出了每一项凭据，但不包含任何具体值。
- 局限与演示内容及候选发布版本记录一致，没有矛盾。
- 每个文件都有负责人和日期。

## 常见误区

- **“有代码和 README 就够了。”** 客户需要的是操作和恢复步骤，包括数据更新流程，而这恰恰是最先出问题的地方。
- **“不写局限，客户才会有信心。”** 缺失的局限会导致意外和互相指责。写明的局限是合同的一部分。
- **“交接是最后一天的任务。”** 边做边写。到最后再补，既慢又容易出错。
- **“操作指南凭记忆就能写。”** 一边实际执行步骤一边写，不要把密钥写进安装说明，并让局限与你在演示中说的保持一致。

## 典型面试题

<details>
<summary>交接包里应该包含什么？</summary>

包含输入与输出说明的操作指南、安装说明、权限、常见故障的 runbook、兜底与重启流程、已知局限、运行证据和版本记录。每一项都是写给将来运行它的人看的，而不是写给构建它的人看的。

</details>

<details>
<summary>你怎么知道交接是有效的？</summary>

请一个没参与开发的人，从零开始按照交接包操作，直到成功跑通一次。他们卡住的任何地方，都是交接包的缺陷。

</details>

<details>
<summary>在交接这件事上，你会做哪些不同的安排？</summary>

挑一个真实的缺口，比如更早地写好文档更新步骤，因为这部分最难解释清楚。

</details>
