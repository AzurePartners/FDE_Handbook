**一句话：** 外部 API 会更换版本，限制你的调用频率，有时还按调用次数收费，所以一个经得起时间考验的集成要固定版本、遵守限流并准备备用数据源，而不是把某家供应商当前的行为硬编码进业务逻辑。

## 是什么

每一个外部依赖都是一个会不断变化的目标。**版本** 会变：你所依赖的端点可能被弃用或改动，所以要固定到某个具体版本，并有计划地升级。**限流** 限制单位时间内的请求数（这个概念以及 429/退避的基础知识见模块一：[限流](../../m1/03-apis-data-integration/04-rate-limits.md)）；这里的重点是在应对版本漂移的同时，也为限流做好设计。有些工具是 **收费的**，所以调用量就是成本。而且任何单一来源都可能失败或出错，所以关键路径最好有 **备用数据源**（备用供应商、缓存、降级模式）。总的原则是：不要把某家供应商的特有行为和当前能力固化进你的核心逻辑，而要把它们封装起来，让它们可以变动。

## FDE 为什么需要

集成如果默认供应商永远不会变，等供应商不可避免地变了，就会在生产环境里出问题。把某个供应商的行为硬编码进业务逻辑，会让更换或升级变得痛苦，还会把你的可靠性和对方的可靠性绑在一起。一个 FDE 从一开始就为版本漂移、限流和供应商失败做好设计，这样 API 变更或宕机，只是改一项配置或切换到备用数据源，而不会变成你这个功能的宕机。

## 核心概念

- **固定版本，有计划地升级：** 避免用“latest”；清楚行为何时会变。
- **遵守限流：** 节流、批处理、遇到 429 就退避；不要无节制地调用。
- **成本意识：** 收费的工具意味着调用量就是支出；要缓存，并尽量减少调用。
- **备用数据源：** 为关键路径准备备用供应商、缓存或降级模式。
- **不要硬编码供应商的能力：** 把供应商包在你自己的接口后面（与连接器契约相关）。

## 常见误区

- **“这个 API 会一直像今天这样工作。”** 版本会被弃用，也会变；要固定版本，并规划升级。
- **“我们不会撞上限流。”** 真实负载下一定会撞上；要在一开始就设计好节流和退避。
- **“关键路径只用一家供应商就够了。”** 单一来源会失败；要准备备用数据源或降级模式。

## 典型面试题

<details>
<summary>你会怎样让集成在供应商修改 API 时依然稳健？</summary>

固定到某个具体的 API 版本并有计划地升级；把供应商包在你自己的连接器接口后面，让业务逻辑不依赖它特有的行为；用节流和退避来遵守限流；为关键路径准备备用数据源或降级模式。这样，API 变更或宕机就只是一次可控的配置调整或来源切换，而不是整个功能的宕机。

</details>

<details>
<summary>开始撞上供应商的限流时，你会怎么做？</summary>

遇到 429 就做指数退避并加上抖动，尽可能批处理请求，缓存重复的结果，并把负载摊开或排队。如果这个限制对该应用场景来说是结构性的，就申请更高的档位或增加第二个来源，而不是激进地重试，把情况越搞越糟。

</details>
