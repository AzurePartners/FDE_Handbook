**一句话：** 提示词版本管理是给每一次提示词改动一个永久的版本 ID 和一条书面理由；实验则是一次只测试一处改动，并准确记录当时运行了什么、得到了什么。

## 是什么

生产环境里的提示词影响着每一个答案，所以改一句话就像一次代码部署，会改变系统的行为。12-Factor Agents 指南说，要“自己掌控你的提示词，并把它们当作一等代码来对待”。

打个比方，拿一张带修订备注的食谱卡来说：“v7，少放盐，食客觉得汤太咸。”每道菜都能追溯到当天用的那张卡；如果 v7 更差，厨师就退回 v6。

这是两个习惯。版本管理：提示词文件放在 Git 里，每条调用日志（每次模型调用留下的记录）都打上版本 ID，再用变更日志写明每次改动的理由。实验：一次只改一处，并记录模型、设置、提示词版本、输入、输出和评测运行（对固定用例打分的测试）。

## FDE 为什么需要

一家保险公司的助手负责把邮件里的理赔申请分派到各个队列，三个人在模型供应商的仪表盘里编辑它的提示词。某个周二，被错分到通用队列的情况激增。日志里只有“prompt: triage”和一个模型别名（模型供应商可以改指向的名称），所以没人知道是哪次编辑造成的。

FDE 把提示词搬进客户的代码仓库，文件是 `prompts/claims_triage.md`（v15），在配置里固定模型 ID，并从编辑历史中找回更早的版本。把每个版本都在评测集上重跑一遍，发现质量下降是随一行新增内容出现的：“如果不确定，就送到通用队列。”FDE 把它撤销，发布为 v16。COO 问起改了什么、为什么改时，变更日志就是答案。

## 核心概念

### 版本 ID 与整套组合

ID 可以是文件头里的一个编号（v16），可以是 Git 的 commit 哈希，也可以两者并用：`claims-triage@v16+3f2a9c1`。把这个不会变的 ID 记进每一次调用的日志（见程序化 LLM 接口），绝不要记 `production` 这样可移动的标签。

输出还取决于少样本示例（few-shot examples）、输出 schema、工具定义、模型和设置，所以要把它们一起纳入版本管理，或者逐项记录。

### 变更日志

每条记录写明改了什么、为什么改（对应的失败、工单或假设）、谁改的、什么时候改的，以及证据。没有理由，下一个编辑者就会把他们看不懂的修复撤销掉。

```text
claims-triage v16  2026-09-14  J. Park (FDE)
改动：删除“如果不确定，就送到通用队列。”
原因：v15 之后，被错分到通用队列的情况增多（OPS-412）
证据：实验 EXP-031
```

### 每个实验只改一处

如果提示词和模型同时改动，分数变了，你就说不清是哪一个造成的，而且一处的提升可能掩盖另一处的退步。遇到模型升级加提示词修复的情况，先让没改过的提示词在新模型上跑，再跑修复版。这样可能漏掉两者之间的交互影响，但对小的评测集来说，是正确的默认做法。每个实验都要写明自己的基线。

### 实验记录

| 字段 | 写什么 |
|---|---|
| ID、日期、作者 | `EXP-031`，运行日期 |
| 改动与基线 | v15 到 v16，并附上假设 |
| 提示词版本 | `claims-triage@v16+3f2a9c1` |
| 模型 | 确切的快照 ID（固定的模型版本） |
| 发送的设置 | 最大输出 token 数、推理强度；temperature 仅在模型接受时才记录 |
| 输入与输出 | 评测集版本；保存下来的原始回复 |
| 评测运行 | 指向得分的链接（在回归测试里对比） |
| 决定 | 上线、否决或重跑 |

要把输出存下来，因为重跑无法复现它们：Anthropic 指出，temperature 设为 0 也“从不保证输出完全一致”，服务端的更新可能让同一个模型 ID 下的行为发生细微变化，下线的模型也不会再作答。记录里的客户数据要遵守客户的数据处理规定。

Langfuse、LangSmith 和 MLflow 这类提示词注册表（registry）会保存带编号的版本，并配上可移动的标签，在非工程师经常修改提示词时很有用。

## 常见误区

- **“提示词版本就是提示词文本。”** 示例、schema、工具、模型和设置同样决定输出。
- **“有 Git 历史就够了，日志不需要版本 ID。”** Git 能显示改了什么，但显示不了是哪个版本产生了糟糕的答案。
- **“`production` 标签能告诉我运行的是哪个提示词。”** 标签是会移动的。要记录不可变的 ID。
- **“记下提示词和模型，我就能复现任何输出。”** 输出每次运行都不一样，模型还会下线。要把输出存下来。

## 典型面试题

<details>
<summary>什么是提示词版本管理？为什么要把提示词当作代码来对待？</summary>

每次改动都有一个永久的 ID 和一条写在变更日志里的理由，这个 ID 随每次调用一起记入日志。改一行内容就像一次部署，会改变每一个请求，所以你必须知道运行的是什么，并能快速回滚。

</details>

<details>
<summary>提示词版本和“production”标签有什么区别？</summary>

像 v7 这样的版本永远不变。标签是一个可以移动的指针，用来把某个版本推上线或回滚。我记录的是版本，就像记录 commit 哈希，而不是分支名。

</details>

<details>
<summary>模型升级和提示词修复都要做，你怎么测试它们？</summary>

分开测：先用没改过的提示词跑新模型，再跑修复版，每次都对照一个写明的基线，这样每次分数变化都只有一个原因。

</details>

<details>
<summary>客户的提示词你会放在 Git 里，还是放在模型供应商的控制台里？</summary>

默认放 Git；非工程师经常修改时，则用团队自己掌控的注册表。不要放控制台：2026 年 OpenAI 弃用了仪表盘里的提示词对象，Anthropic 也下线了 Workbench 里保存的提示词。

</details>
