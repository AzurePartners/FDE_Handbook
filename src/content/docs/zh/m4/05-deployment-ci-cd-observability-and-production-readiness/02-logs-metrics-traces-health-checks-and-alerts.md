**一句话：** 可观测性就是从外部回答“系统现在在做什么，它健康吗？”，靠的是日志（事件）、指标（随时间变化的数值）、trace（一次请求的路径）、健康检查（它还活着吗？）和告警（出问题时通知我）。

## 是什么

这些信号让运行中的系统变得看得清、读得懂（模块一已把部署 **日志** 作为基础讲过，见 [部署日志](../../m1/05-containers-deployment/08-deployment-logs.md)；本页补充指标、trace、健康检查、告警，以及 AI 专属的信号）：

- **日志：** 带时间戳的事件记录（“收到请求”“模型调用失败”）。
- **指标：** 随时间聚合的数值（每秒请求数、错误率、p95 延迟；对 AI 来说还有 token、成本、质量）。
- **trace：** 单个请求跨越各个步骤/服务的路径，显示时间花在哪里、失败发生在哪里。
- **健康检查：** 一个简单的端点，报告服务是否活着、它的依赖项是否可达。
- **告警：** 指标越过阈值时自动发出的通知，让你在用户反馈之前就知道出了问题。

对 AI 系统来说，还要加上 token、成本、模型/提示词版本和质量指标这类信号。

## FDE 为什么需要

当某个功能在生产环境里表现异常时，如果没有可观测性，“它昨天给了个奇怪的回答”这句话根本没法着手处理。正是（脱敏后的）日志记录、追踪和指标，让你能够复现并修复问题；告警则让你主动发现问题。一开始就加好埋点的 FDE，能运维和调试这个系统；没加的人只能在黑暗中猜。

## 核心概念

| 信号 | 回答的问题 |
| --- | --- |
| 日志 | 发生了什么？ |
| 指标 | 长期来看它健康吗？ |
| Trace | 时间花在了哪里 / 在哪里失败了？ |
| 健康检查 | 它现在在运行吗？ |
| 告警 | 出问题时通知我 |

- **关联 ID：** 把同一个请求的日志/trace 串在一起。
- **对 PII 和密钥脱敏：** 绝不记录敏感数据。

## 常见误区

- **“有日志就够了。”** 日志给你的是一个个事件；你还需要用指标看趋势，用 trace 看路径，用告警来主动获得通知。
- **“出了问题再加埋点。”** 没有埋点的事故是没法调试的；要事先加好。
- **“什么都记，包括完整的提示词和 PII。”** 敏感数据要脱敏；只记录调试需要的内容，并且要安全地记。

## 典型面试题

<details>
<summary>日志、指标和 trace 各自能告诉你什么？</summary>

日志记录一个个离散的事件（发生了什么）。指标把数值随时间聚合起来（是否健康、趋势如何）。trace 跟随一个请求穿过各个服务（时间花在哪里，在哪里失败）。再加上健康检查（它还活着吗）和告警（越过阈值时通知），它们合起来回答“系统现在在做什么，它健康吗？”

</details>

<details>
<summary>客户反馈昨天有一条输出不对。要调查这个问题，你当时必须已经记录了哪些信息？</summary>

带关联 ID 的请求、脱敏后的提示词和检索到的上下文、模型和提示词的版本、输出，以及延迟和 token 指标，这样我才能复现当时的确切条件。如果当时没有记录这些，我就只能靠猜。

</details>
