**一句话：** 关系数据库把数据存放在相互关联的表里，这样相关的事实就不用在每个需要它的地方都重复一份。

## 是什么

关系数据库把数据组织成表，有点像电子表格，每张表存放一类东西：客户、订单、产品。每张表有一组确定的列，也就是它的 schema，每一行是一条记录。之所以叫“关系”，是因为表与表之间通过共享的标识符相互关联，所以数据库能回答“这个订单是哪个客户下的”，而不用在每一行订单里都存一份客户的完整信息。

可以把它想象成一个文件柜，每个主题一个抽屉：“客户”抽屉里每个客户一个文件夹，“订单”抽屉里每个订单一个文件夹，每个订单文件夹里有一张小纸条，指明它属于哪个客户，而不是夹一份该客户信息的完整副本。这张纸条就是外键。FDE 接触到的几乎所有业务系统，底层都是关系数据库。

## FDE 为什么需要

把一个新系统接到现有系统上时，理解 schema 很关键，因为新系统存数据的结构必须与现有结构一致，或者有意识地映射过去。客户问“为什么这条记录出现了两次”，往往是一个建模问题：要么是 bug，要么是两条本来就不同的行碰巧共用了一个 key。快速读懂 schema 是日常工作，也是学习 SQL 基础那一页的前提。

## 核心概念

### 表与 schema

schema 是一张表的结构：它有哪些列，各是什么类型。一张 `customers` 表的 schema 可能是这样：

```sql
CREATE TABLE customers (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT
);
```

### 主键

主键是唯一标识表中每一行的那一列（或几列的组合），通常是一个自增 ID。

### 外键

外键是一张表中指向另一张表主键的列，由它建立起关联：

```sql
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    customer_id INTEGER,
    total REAL,
    FOREIGN KEY (customer_id) REFERENCES customers(id)
);
```

这里，`orders.customer_id` 指回 `customers.id`。这样你就能查“给我看这个客户的订单”，而不用把姓名和邮箱复制到每一行订单里。复制的话，一旦邮箱变了而只更新了部分行，各份副本就会不一致。

### 为什么不用一张大表

人们的第一反应往往是把客户和订单信息放进同一张表。可一旦邮箱变了，过去的每一行订单都得跟着改，否则数据就会自相矛盾。拆成相互关联的表、每个事实只存一次，这正是关系模型的核心思想，也是规范化背后的思想，详见数据规范化那一页。

## 常见误区

- **“外键和主键是一回事。”** 主键在自己的表内唯一标识一行。外键引用的是另一张表的主键，用来把记录关联起来。
- **“关系数据库就是更大的电子表格。”** 电子表格的各个工作表之间没有强制的关联。关系数据库在声明了外键约束之后，可以强制要求外键的值在它指向的表里确实存在（SQLite 还需要执行 `PRAGMA foreign_keys = ON`）。
- **“NULL 就是零或空字符串。”** 它表示未知或缺失；怎么查询它见 [SQL 基础](./11-sql-basics.md)。

## 典型面试题

<details>
<summary>主键和外键有什么区别？</summary>

主键在自己的表内唯一标识每一行。外键存放的是另一张表的主键值，把两张表关联起来。

</details>

<details>
<summary>为什么要把客户信息存在单独的表里，而不是在每一行订单上重复一遍？</summary>

在每行订单上重复客户信息既浪费空间，又有副本不一致的风险：邮箱一变，如果只更新了部分行，数据就对不上了。只存一次、用外键关联，就只有一个唯一可信的数据源。

</details>

<details>
<summary>一个新系统需要接入客户现有的数据库。你先看什么？</summary>

先看现有的 schema：有哪些表，外键是怎么把它们关联起来的。新数据要么符合这个结构，要么明确地映射过去。

</details>
