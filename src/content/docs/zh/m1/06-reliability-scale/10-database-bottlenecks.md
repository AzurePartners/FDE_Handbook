**一句话：** 应用服务器是无状态的，很容易加；但数据库保存着真正的状态，所以应用一旦做了水平扩展，它往往就成了真正的限制。

## 是什么

增加应用服务器很简单：它们是可以互相替换的副本，本身不带数据（见“负载均衡与水平扩展”）。数据库却不能简单地复制五份、让每一份各自独立接受写入，否则这些副本对数据的认识就会互相矛盾。因此，随着流量增长，它最有可能成为瓶颈。

大多数数据库变慢都源于少数几个问题：慢查询、缺失索引、N+1 查询和锁争用。

## FDE 为什么需要

“应用很慢”只要仔细一查，几乎总会变成“数据库某一部分的工作很慢”。客户怪服务器，加了更多应用服务器，结果毫无改善，因为应用服务器从来就不是瓶颈。能认出具体是哪个问题，决定了你是在修复故障，还是在拖长故障。

## 核心概念

### 慢查询

一个扫描行数远超所需的查询，会随着表的增长越来越慢。在测试中面对一千行数据表现正常的查询，面对一百万行可能要花好几秒。大多数数据库都能展示查询的执行计划，从中可以看出走的是全表扫描还是索引。

### 缺失索引

索引让数据库可以直接跳到匹配的行，而不是逐行扫描，就像查书后的索引和逐页翻书的区别。如果查询在一个没有索引的列上过滤或排序，就只能全表扫描。索引能加快读取，但会增加写入的开销，所以要有针对性地加在那些经常被搜索或关联（join）的列上。

### N+1 查询

当代码先取出一个列表，再遍历这个列表、为每一项多发一次查询时，就出现了 N+1 查询。例如取出 50 个订单，再逐个查询每个订单的客户：1 次查询加上另外 50 次。解决办法是用一次 join 或批量查询把关联数据一起取出来。

```python
# N+1: one query per order
orders = db.query("SELECT * FROM orders")
for order in orders:
    customer = db.query(
        "SELECT * FROM customers WHERE id = %s", order.customer_id
    )

# Fixed: one query total
rows = db.query("""
    SELECT orders.*, customers.*
    FROM orders JOIN customers ON orders.customer_id = customers.id
""")
```

### 锁争用

数据库在写入某一行时会锁住它，所以第二个写入要等待。这很正常，通常也很短暂。当很多操作争抢同样的行，或者某个事务持有锁的时间超过必要时，它就会成为瓶颈。

### 只读副本

概括地说，只读副本是与主库保持同步的数据库副本，负责处理读查询，从而分担主库的负载。写入仍然发往主库，而副本会稍微落后于主库。这对读多的应用有帮助，但解决不了写入瓶颈，而且慢查询在副本上照样慢。

另外两种相关的解法有各自的页面：“连接上限与连接池”，以及用“缓存”把重复读取彻底省掉。

## 常见误区

- **“加应用服务器能解决数据库慢的问题。”** 这只会让更多调用方去等同一个慢数据库，情况可能更糟，而不是更好。
- **“索引总能让速度变快。”** 索引能加快匹配的读取，但会拖慢对这张表的写入，所以给每一列都加索引并不是没有代价的。
- **“只读副本也能扩展写入。”** 副本只处理读取。写入仍然都要经过主库。

## 典型面试题

<details>
<summary>什么是 N+1 查询问题？如何解决？</summary>

先取出一个列表，然后在循环里为每一项再多发一次查询，而不是用一次查询取出所有数据。解决办法是用 join 或批量查询把它们合并成一次查询。

</details>

<details>
<summary>数据库索引有什么作用？为什么不给每一列都加索引？</summary>

它让数据库能直接跳到匹配的行，而不是扫描整张表。每个索引都会增加写入的开销，所以只在真正经常被查询的列上有针对性地添加索引。

</details>

<details>
<summary>客户加了更多应用服务器，但应用还是很慢。在数据库这一侧你会检查什么？</summary>

检查慢查询及其执行计划、缺失的索引、代码里有没有 N+1 模式，以及连接是否被耗尽，或者请求是否卡在锁后面。

</details>
