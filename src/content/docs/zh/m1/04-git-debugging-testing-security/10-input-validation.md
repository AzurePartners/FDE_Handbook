**一句话：** 输入校验就是在使用来自用户、表单或外部服务的数据之前，先检查它是否符合代码的预期。

## 是什么

任何来自你自己代码之外的数据，无论是表单字段、URL 参数、请求体，还是另一个服务返回的响应，都不要不经检查就信任。校验是指检查一个值的类型、长度、格式和取值范围，拒绝任何不符合要求的值，而不是让它在系统更深处、更不显眼的地方出错。

```python
def get_weather(city: str):
    if not city or len(city) > 100:
        raise ValueError("city must be a non-empty string of at most 100 characters")
```

这里的检查故意写得很简单：在这个值进入数据库查询或 API 调用之前，拒绝空的城市名和长得离谱的城市名。少了检查，错误输入并不会消失，只是让失败转移到更难诊断的地方，往往变成一段本不该让用户看到的原始堆栈跟踪。

## FDE 为什么需要

AI 编程工具追求的是“让这个功能跑起来”，它并不知道客户的真实用户会发来什么样的输入。它在网上读过大量直接信任表单字段的代码，因为那些演示从来没测过别的情况。如果不加审查，它就会把这种偷懒的写法搬进真实系统，而在生产环境中，第一个格式不对的请求（甚至不需要是恶意的）就可能导致崩溃，或者往数据库里写入错误的数据。

## 核心概念

### 要检查什么

- **类型**：需要数字的地方是不是真的数字，而不是一个看起来像数字的字符串。
- **长度**：字符串是否在合理的长度范围内，避免一个长得离谱的值给下游带来问题。
- **格式**：邮箱是否包含 `@`，日期是否符合预期的格式。
- **范围**：数量是否在合理的区间内，比如不能是负数。

### 明确地失败，而不是悄无声息

拒绝错误输入时，应该给出清晰的错误，比如返回 400 并说明哪里不对，而不是笼统地崩溃，或者悄悄猜测用户“大概想要什么”。悄悄猜测可能产生一个看起来正确、实际错误的结果，比明显的失败更难发现。

### 外部数据也要校验，不只是表单

来自内部服务或外部 API 的数据同样可能格式有误，比如某个字段有时会缺失。凡是不是在你自己代码中写死的可信常量，都要校验，而不只是来自面向公众的表单的数据。

## 常见误区

- **“只有面向公众的表单才需要输入校验。”** 来自内部服务的数据或 API 响应同样可能格式有误。凡是不是在你自己代码中写死的可信常量，都要校验。
- **“Python 的类型提示会在运行时强制检查类型。”** 像 `city: str` 这样的类型提示只是写给读者和工具看的说明，不是运行时检查。传入别的类型照样能运行，直到某个显式检查把它拦下来。
- **“AI 写的代码默认就会校验输入。”** AI 工具倾向于写出能让正常路径演示跑通的那个版本，除非你明确要求，否则它会跳过各种检查。

## 典型面试题

<details>
<summary>AI 工具写了一个能用的端点，但没有任何输入校验。风险是什么？你会怎么做？</summary>

没有校验，这个端点就会接收格式错误或恶意的输入，并把它传到系统更深处，导致崩溃或错误的数据库写入。加上对类型、长度和格式的显式检查，校验失败时返回清晰的错误，并在合并前用测试确认。

</details>

<details>
<summary>为什么来自另一个内部服务的数据也要校验，而不只是用户输入？</summary>

内部服务同样可能发来格式错误的数据，比如上游改动之后某个字段时有时无。把“内部”当成天然可信，就会漏掉那类只有在两个系统对数据结构理解不一致时才会暴露的集成 bug。

</details>

<details>
<summary>好的校验错误信息和差的有什么区别？</summary>

好的错误信息会说明哪里不对，比如 “city must be at most 100 characters”，让调用方知道如何修正请求。差的则是笼统的崩溃，或者一个毫无帮助的 500，完全看不出该改什么。

</details>
