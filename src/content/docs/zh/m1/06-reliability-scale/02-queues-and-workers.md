**一句话：** 队列存放等待执行的任务，worker 是一个独立进程，负责从队列里取出任务并执行。

## 是什么

工作一旦移出请求路径（见“同步与异步”），就得有东西来真正执行它。队列是一个有序的暂存区，存放等待执行的任务。一个任务（job）就是一个工作单元，带有输入和唯一 ID，之后可以据此查询进度和结果。worker 是一个独立进程，从队列中取出任务、完成工作并记录结果。

这种拆分正是该模式的价值所在。接收请求的服务器始终空出手来处理下一个请求。worker 可以跑在另一台机器上；队列积压时可以加 worker，而不用动接收请求的那部分代码。

死信队列用来存放失败次数过多的任务，方便有人去排查原因，而不是让任务无限重试或者悄无声息地消失。

## FDE 为什么需要

把任务放进队列，不等于任务被处理了。任务可能一直搁在那里、悄悄失败，或者因为负责它的 worker 崩溃而永远没人取走。“队列接住了”不等于“系统处理了”。在客户项目里，这表现为报表一直没生成、邮件一直没发出，而界面上没有任何提示说明原因。只有失败的任务始终可见，系统才算可靠，这通常要靠死信队列和监控，光有队列是不够的。

## 核心概念

| 术语 | 含义 |
|---|---|
| 任务（job） | 一个工作单元，带有输入和唯一 ID |
| 队列 | 存放待执行任务的有序暂存区 |
| worker | 取出任务并执行的独立进程 |
| 死信队列 | 存放失败次数过多的任务，留待人工排查 |

worker 和其他进程一样，会崩溃，也会被重新部署。如果某个任务恰好在那一刻执行到一半，就需要有重试方案（见“重试与退避”一页），否则它就直接丢了。

只有当 worker 本身是瓶颈时，加 worker 才能加快消化积压的队列。如果每个任务都要调用一个有限流的外部 API，或者访问一个已经到达连接上限的数据库，加 worker 只会制造更多卡在同一个上限前排队的调用方。

## 常见误区

- **“放进队列就可靠了。”** 队列只是在有人执行之前把工作存着。可靠性来自重试、死信处理，以及真正有人在看的监控。
- **“worker 崩溃很少见，可以不管。”** worker 崩溃和重新部署是家常便饭。那一刻正在执行的任务需要有重试方案。
- **“worker 越多，积压清得越快。”** 前提是 worker 本身是瓶颈。如果它们都在等同一个限流的 API 或数据库，加 worker 只是增加了排队的人。

## 典型面试题

<details>
<summary>什么是死信队列？为什么它很重要？</summary>

它是一个单独的地方，任务失败超过设定次数后会被放进去，而不是无限重试或直接消失。它的重要性在于让失败变得可见，这样才有人能去修复出问题的地方。

</details>

<details>
<summary>客户说“我们已经放进队列了，所以没问题”。你会问什么？</summary>

有没有针对失败或卡住的任务的监控？有没有死信队列，或者针对反复失败的告警？worker 在任务执行到一半时崩溃会怎样？谁来检查失败的任务，多久检查一次？

</details>

<details>
<summary>为什么增加 worker 不一定能加快消化积压的队列？</summary>

如果真正的瓶颈是所有 worker 共用的某样东西，比如有限流的外部 API 或数据库连接上限，加 worker 只意味着更多调用方卡在同一个上限前。解决办法是处理这个共享瓶颈，而不是加 worker。

</details>
