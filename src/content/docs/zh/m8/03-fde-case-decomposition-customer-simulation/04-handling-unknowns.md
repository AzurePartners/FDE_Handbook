**一句话：** 当你不知道时，得分的答案是"我还不知道——这是我一周内弄清它的方法"：承认缺口，说出最便宜的能填补它的实验，给出日期，而不是当场编一个自信的答案。

## 是什么

每一轮 FDE 面试都会有你答不上的问题：客户的数据量、某个 API 是否支持你需要的调用、某条法规如何适用、模型能否处理某类文档。处理未知是一个三段式回答——直白说出缺口、带方法和时长的验证计划、以及在此期间你会做什么——不道歉，也不虚张。它是模块五"明确说出哪些结论仍未验证"在面试中的形式。

## FDE 为什么需要

客户根据你说的话做决策。Discovery 会议上一个自信的错误答案，六周后就变成错误的架构。因此面试官会一直追问，直到找到你知识的边缘，然后看你怎么办。虚张会被任何做过这事的人当场识破；验证计划被评为最强的答案，因为它就是这份工作每周都要做的事。

## 核心概念

### 三段式回答

1. **缺口：** "我不知道他们的理赔系统是暴露 API 还是只有每晚导出。"
2. **计划：** "第一周我会拿到一个环境的只读权限，取 schema 和 100 行样本，测一次调用。这能告诉我们是实时集成还是批处理。"
3. **同时：** "我会把摄取边界设计成两条路径都能接入，并在 ADR 里保持这个决策开放，直到拿到样本。"

### 最便宜的实验优先

一份样本导出、一次 API 调用、该文档类型上的 20 条 eval、与真正用户的一次访谈。计划以天计，不以 sprint 计。

### 区分未知的类型

能查到的事实（API 的 rate limit）、只有客户知道的事实（他们的量）、不测就没人知道的事（模型能否处理他们的 PDF）。说出是哪一类；计划各不相同。

### 当场标注

"假设""已验证""未验证"在白板环节很有用。边走边标记每个结论，让面试官看到你在跟踪证据强度。

### 已知限制作为交付物

在项目里，未知清单会变成交接包的已知限制一节。在面试里，提到你会写这一节本身就是信号。

## 常见误区

- **"承认不知道显得弱。"** 虚张在被抓到的那一刻才显得弱，而那通常就是下一个问题。计划显得强。
- **"我应该处处保留。"** 保留不等于给未知划定范围。对知道的自信，对不知道的精确，对怎么查清楚具体。
- **"验证计划可以是'再研究一下'。"** 必须有方法、样本和时长。"我会去了解一下"不是计划。

## 典型面试题

<details>
<summary>模型能足够准确地处理客户的扫描理赔表吗？</summary>

"还不知道；扫描表因扫描仪和模板差异很大。第一周我会从他们前三个模板里各取 30 份代表性表单，跑 OCR 加抽取，让理赔分析师标注字段。这能得到字段级准确率，并告诉我们是否需要版面感知的解析器或对特定字段的人工检查。在那之前，我会把抽取放在审核步骤之后。"

</details>

<details>
<summary>按他们的量，这每月要花多少钱？</summary>

给公式，不给数字：每任务调用数 × 每次调用 token 数 × 单价，加检索和存储。说明填上公式需要什么（月度量、平均文档长度），并给一个来自可比部署的有界估计，标明是估计及其假设。

</details>

<details>
<summary>他们的数据驻留规则允许这么做吗？</summary>

说出你对这类规则常见形态的了解、具体需要确认什么（哪个司法辖区、衍生数据算不算、供应商的区域选项是否满足），以及谁来确认：他们的法务或合规负责人，书面确认，在设计冻结之前。

</details>
