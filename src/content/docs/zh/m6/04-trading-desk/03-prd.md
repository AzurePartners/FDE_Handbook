**一句话：** Trade Recommendation Desk PRD（FDE 实习项目，2026 年 9 月）定义了六 agent 研究台必须做什么、八条永不违反的产品规则，以及团队如何判断项目已完成。

> **原始文档：** *Trade Recommendation Desk, Product Requirements Document*，Azure Partners，Sprint 1 最终版。本页是阅读指南。它是本 Module 的参考 PRD：写自己的 PRD 时，可以从它的结构开始。

## 文档结构

| 章节 | 确定了什么 |
|---|---|
| 1. 概述 | 六 agent 的 Puffo 团队；每周对 10 只股票给出 BUY / SELL / NO TRADE；判断来自后端策略引擎；一个模拟组合；每个判断都会打分。内部项目、无资金、非投资建议、不接受被研究公司的任何付款。 |
| 2. 问题 | AI 交易观点的五种失败方式，以及用系统控制来防止它们的承诺。 |
| 3. 用户 | 投资经理（由导师扮演）、两名实习工程师、导师评审。 |
| 4. 产品规则 | 适用于所有地方的八条规则。 |
| 5. 范围 | 做什么和不做什么，都明确写出。 |
| 6–7. Agents 与流程 | 六个角色；两类运行；从初始观点到打分的八个步骤。 |
| 8. 需求 | 数据、策略与回测、判断内容、模拟交易、结果跟踪、发布检查、前端。 |
| 9. 平台事实 | 影响产品的 Puffo 行为。 |
| 10. 成功指标 | 始终为真的属性、策略结果、agent 与前向结果、实习生的学习。 |
| 11. 验收标准 | 25 项编号检查。 |
| 12–13. 后续阶段与术语表 | 推迟的内容，以及每个术语的定义。 |

## 八条产品规则

1. 后端掌管每一个数字。agent 通过 evidence ID 引用数字，从不自己敲数字。
2. 每个已发布的数字都链接到其来源、期间和时间。
3. 每次运行只使用截止时间之前已经存在的数据。
4. 判断由规则产生。agent 可以降低信心等级或把判断改为 NO TRADE，但永远不能提高。
5. 规则在 holdout 测试前冻结，holdout 只运行一次。
6. 每个结果都包含交易成本和基准。
7. NO TRADE 是一个有效答案。
8. 没有真实交易，没有真实资金。

每条规则都对应第 2 节中的一种失败。规则 1 和 2 对应无出处的数字；规则 3 对应前视偏差；规则 5 对应过拟合；规则 6 对应忽略成本和大盘涨跌；模拟组合和结果跟踪对应"从未核对"。

## 值得细读的需求

**数据（8.1）。** 股票池由一条书面规则在设计期之前的某个日期选定，绝不根据之后的表现挑选。每个数字使用首次报告值，之后的重述永远不会替换早期日期的数值。盘后发布的财报从下一个交易日开始计算。期间用起止日期存储，绝不只用"Q1"这样的标签。

**判断内容（8.3）。** 每个判断包含信心等级、周期、参考价、失效价位、复核日期、带来源的支持和反对证据、每个 agent 的观点、Risk 用原话写的评估、数据质量标记和披露声明。修改后的判断会创建一条新记录并关联旧记录，旧记录永不改变。

**发布检查（8.6）。** 九种情况会拦截判断，从 agent 文本中出现数字，到记录不符合规定格式。每次拦截都会带原因发布在主频道中。

**模拟交易与结果（8.4–8.5）。** 从第 6 周起，一个模拟组合跟随已发布的判断。每个判断在复核日后打分：相对 SPY 的收益、是否触及失效价位、判断是否正确；对 NO TRADE，记录股票实际表现如何。

## 值得注意的地方

**范围清单写明了砍掉了什么。** 定时任务、纯规则对照组合、自动成本跟踪、期权、加密货币、非美股、电话会议记录和分析师预期都不在范围内。纯规则对照组合是一个诚实的省略：没有它，这一阶段就无法衡量 agent 相比规则到底增加了什么价值。PRD 把它放在后续阶段，而不是假装它存在。

**平台事实出现在产品文档里。** 第 9 节写明：agent 只在收到消息时才行动、会被自己频道里的每条消息唤醒、每次唤醒只有 10 次工具调用、共享一台机器和一份额度。这些不是实现细节：正是它们决定了每周流程由人启动、每个专家需要自己的频道。

**成功是分层的。** "始终为真"的属性由测试证明。策略成功有一个最低标准（报告能清楚显示策略在未调参的数据上、扣除成本后是否跑赢基准）和一个"良好"标准，而具体门槛在看到验证期结果之前就设定。实习相关的指标则问：每位实习生能否把一个数字追溯到它的原始公告。

**负面结果也是可接受的结果。** 最低策略标准是一个清晰的答案，而不是一次胜利。诚实地证明规则没有跑赢基准的研究台，同样满足了需求。

## 常见误区

- **"NO TRADE 说明研究台没做出决定。"** 规则 7 把它定为有效答案，每个 NO TRADE 都必须能追溯到某条规则、某项风险检查或某个数据条件。
- **"验收标准就是测试计划。"** 它们是完成的定义。Technical Design 中的测试计划说明每一条如何证明。
- **"前端可以读取 agent 的消息。"** 它只从后端读取，所以不可能显示任何未经发布检查批准的内容。

## 典型面试题

<details>
<summary>为什么股票池要由一条在设计期之前应用的书面规则来选定？</summary>

根据表现挑选股票，会把幸存者偏差和后见之明带进结果。在更早的日期应用、并在任何回测前记录下来的规则，意味着这个股票池在当时、凭当时可得的信息就能被选出来。

</details>

<details>
<summary>"具体门槛在看到验证期结果之前设定"防的是什么？</summary>

防止临时改门槛。如果看到结果之后才定成功标准，就可以把它定成策略碰巧达到的水平。先定门槛，并由导师在第 3 周末批准，结果才是真正的检验。

</details>

<details>
<summary>你会先测哪一条验收标准？为什么？</summary>

第 17 条：被篡改的数值会阻止发布并显示原因。它证明的是核心承诺，即错误的数字不会到达读者，并且端到端地覆盖了 evidence store、组装和发布检查。

</details>
