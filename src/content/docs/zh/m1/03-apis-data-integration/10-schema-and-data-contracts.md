**一句话：** schema 是两个系统约定好的某份数据的结构，这个约定就是一份契约，哪怕从来没有人把它写下来。

## 是什么

两个系统交换数据时，会默认约定一个结构：有哪些字段，每个字段是什么意思、什么类型、用什么单位，以及值缺失时怎么办。这个约定就是契约。两个系统可能都有一个叫“customer”的字段，含义却不同：一个指付账单的人，另一个指使用产品的人。两边都没错，只是从来没有统一过定义。

契约一旦被打破，就会显现出来。如果一个天气 API 悄悄把温度字段从摄氏度改成华氏度，下游所有假定摄氏度的计算都会出错，却不会抛出任何错误，因为 29.4 无论如何都是合法的数字。这个 bug 表现为一个错误的答案，而不是崩溃，所以更难发现。

## FDE 为什么需要

FDE 处理的大多数集成 bug 都不是崩溃，而是悄无声息的不匹配：字段在版本之间被改了名，币种是默认的却从未确认，null 被当成了零。把契约明确写下来，就把一个看不见的假设变成了双方都能核对的东西。

## 核心概念

### 字段映射

字段映射是一份明确的清单，写清“系统 A 的这个字段对应系统 B 的那个字段”。例如把 Open-Meteo 和 Frankfurter 的数据合并成一条内部的 `Briefing` 记录：

| 源字段 | 源系统 | 目标字段 | 备注 |
|---|---|---|---|
| `current_weather.temperature` | Open-Meteo | `temperature_c` | 摄氏度，已在文档中确认 |
| `rates.JPY` | Frankfurter | `exchange_rate` | 相对于 `base` 币种 |

在写代码之前先写好这张表，猜测才会变成契约。

### 类型与单位

字段的类型必须两边一致：对大多数程序来说，字符串 `"19.99"` 不等于数字 `19.99`。没有单位的数字是个陷阱：温度可能是摄氏度也可能是华氏度，金额可能是美元也可能是美分。一定要通过文档或已知的测试值确认单位，绝不能只看字段名。

### Null

缺失的值可能有好几种含义：它本来就不存在（没有中间名），还没采集（这条老记录早于该字段出现），或者获取它时失败了。把所有 null 都当成零，会掩盖真实的问题。

### 版本管理

API 和 schema 会随时间变化：字段会被新增、改名或删除。契约需要一种机制来应对这些变化，避免悄无声息地出错：在 URL 中带版本号，比如 `/v1/customers` 和 `/v2/customers`，或者由提供方发布变更日志。

## 常见误区

- **“字段名一样，数据含义就一样。”** 两个系统可能都有一个叫“status”的字段，取值集合却完全不同。要确认实际含义和允许的取值，而不只是名字。
- **“数字不需要文档，一看就懂。”** 没有标明单位的数字，本身就是有歧义的。100 可能是美元、美分，也可能是百分比。
- **“null 和零差不多。”** 把缺失值当成零，可能会悄悄算错，比如求平均值时把那些从未上报的值当作零算进去。

## 典型面试题

<details>
<summary>说数据是系统之间的契约，是什么意思？</summary>

两个系统必须对交换的每个字段的结构、类型、单位和含义达成一致。如果一方改变了假设而没有通知另一方，集成就会产生错误的结果，而且往往不会报任何错。

</details>

<details>
<summary>两个系统都有一个叫“customer”的字段，但含义不同。你会怎么处理？</summary>

写一张字段映射表，定义每个字段的含义以及它如何转换到目标 schema，然后找每个系统的负责人确认。

</details>

<details>
<summary>上游 API 在下一个版本中新增了一个必填字段。你的集成应该怎么应对？</summary>

先固定在当前版本，等你的代码能发送这个新字段后再有计划地迁移；新增必填的请求字段属于破坏性变更。新增的响应字段则不同：忽略未知字段，这样增量变更就永远不会让解析出错。

</details>
