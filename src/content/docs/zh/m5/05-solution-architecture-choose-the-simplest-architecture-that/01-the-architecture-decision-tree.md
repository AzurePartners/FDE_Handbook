**一句话：** 先从可能行得通的最简单架构做起，只在需要时才升级，顺序是规则/脚本 → Web 应用 → RAG → tool calling → 工作流 → 单 agent → 多 agent，因为每上一级都会增加能力，同时也增加成本、延迟和失败面（failure surface）。

## 是什么

对于 AI 辅助的问题，解决方案的复杂度大致可以排成一道阶梯：

1. **规则/脚本：** 确定性逻辑，不需要模型。
2. **Web 应用：** 架在某些逻辑或数据之上的界面。
3. **RAG：** 检索增强生成，从知识库中取答案。
4. **tool calling：** 模型调用函数来执行操作或获取数据。
5. **工作流：** 由模型步骤和代码步骤组成的固定序列。
6. **单 agent：** 模型自己做计划，并带着工具循环执行。
7. **多 agent：** 多个相互协调的 agent。

所谓**决策树**，就是选能解决问题的最低一级，只有问题确实需要时才往上爬。每上一级，换来更多能力，代价是更高的复杂度、延迟和成本，以及更多出错的方式。

## FDE 为什么需要

业界的炒作把人往“什么都上多 agent 系统”的方向拉，但大多数问题在阶梯的很低处就能解决，往往靠规则、Web 应用或简单的 tool calling。过度构建是 FDE 最主要的失败模式之一：本来一个脚本就够，却上了多 agent 系统，结果更慢、更贵、更难调试，也更不可靠。懂得这道阶梯，你就能为“足够用的最简架构”给出理由，抵制不必要的复杂度，而这正是让方案稳健、好维护的原因。

## 核心概念

- **需要时才往上爬：** 每上一级都会增加成本、延迟和失败面。
- **多数问题都在低处：** 规则、Web 应用、RAG 或 tool calling 就能解决很多问题。
- **agent 能力强，代价也高：** 单 agent 和多 agent 只留给真正开放式、多步骤的问题。
- **要说得出理由：** 能讲清为什么选这一级，而不是更低的一级。
- **简单就是可靠：** 活动部件越少，失败模式越少。

## 常见误区

- **“用 agent 吧，它们是当前最先进的技术。”** agent 会增加复杂度和失败模式，多数问题在阶梯的更低处就能解决。
- **“架构越精巧越好。”** 更好的架构是在满足需求的前提下最简单的那个；精巧本身就是一种成本。
- **“先从最顶层做起，以后再简化。”** 先从简单的做起，只有问题逼到那一步才往上爬；过度构建之后很难再退回去。

## 典型面试题

<details>
<summary>你怎么为一个 AI 问题选择架构？</summary>

我从阶梯的最底层开始看起：规则/脚本、Web 应用、RAG、tool calling、工作流、单 agent、多 agent，选能真正解决问题的最低一级，只有确实需要时才往上爬。每上一级都会增加能力，同时也增加成本、延迟和失败面，所以目标是能用的最简架构，并且我说得出为什么不选更低的一级。

</details>

<details>
<summary>什么时候才真正有必要用多 agent 系统？</summary>

当问题真正是开放式、多步骤的，单 agent、工作流或 tool calling 方案都应付不了，并且获得的能力足以抵得上多出来的复杂度、延迟、成本、协调和失败模式的时候。对大多数问题来说，阶梯上更低的方案更可靠，也更好维护。

</details>
