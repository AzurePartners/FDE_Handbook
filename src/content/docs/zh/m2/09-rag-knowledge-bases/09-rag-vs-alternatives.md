**一句话：** RAG 是给模型补充所缺事实的方式之一，其他方式还有长上下文、微调、数据库查询和实时 API 调用；好的助手会把每个问题交给对该答案负责的那个来源。

## 是什么

模型只知道自己的训练数据，而这些数据停留在某个截止时间，所以应用必须提供私有的或最新的事实。检索增强生成（RAG）把最匹配的文档段落粘贴进提示词；它只是几种方式中的一种。

打个比方，就拿银行来说。图书管理员找出政策那一页。柜员现场读取你的余额，从不查上个月的复印件。计算器负责算利息。下面的每种来源，各自负责一类答案。

## FDE 为什么需要

Northwind Academy 的助手依据政策文档作答，但一名外包人员还把每晚导出的成绩和订单数据也建进了索引，好让它“什么都能答”。Amina Rahman 问自己的分期款有没有扣成功，得到的是一行导出数据，里面的 ORD-104118 看起来一切正常；而计费系统显示的是 `payment_failed`。另一名学员几乎一样的订单行也排在了前列，模型还提到了它。

FDE 把所有记录都从索引里移除，对现行政策保留 RAG，而记录类问题则通过对权威数据源（system of record，即正式数据所在之处）的实时只读查询来回答，并限定在已登录学员本人的范围内。

## 核心概念

### 对比表

| 来源 | 最适合 | 不擅长 |
|---|---|---|
| 长上下文（每次请求都放入全部内容） | 小而稳定的资料集 | 成本、长文本下的质量、按用户过滤 |
| RAG（从索引中取排名靠前的文本块） | 庞大或经常变化的文档 | 检索未命中、索引过期、计数 |
| 微调（进一步训练） | 格式、语气、标签 | 事实、引用、新鲜度 |
| 数据库查询 | 过滤、计数、求平均 | 针对文字内容的问题 |
| 实时 API（权威数据源） | 某一个人的当前状态 | 只能得到它开放的内容 |
| 普通代码 | 规则和算术 | 理解意图 |

### 长上下文与 RAG

现在的上下文窗口已经能达到约 1M token，Anthropic 的 Contextual Retrieval 文章（2024）建议，资料少于约 200,000 token 时可以跳过 RAG，并配合提示词缓存来降低重复请求的成本。但每次请求都要为整个语料重新付费，准确率会随长度下降（上下文腐化；见 Lost in the Middle 和 RULER），而且提示词没法对没有权限的用户隐藏某份文档。Li 等人（2024）发现，长上下文的平均质量更好，但 RAG 便宜得多。

### 微调用于调整行为

在为模型补充知识这件事上，RAG 一直优于无监督微调（Ovadia 等人，2024），而用新事实做微调还会增加幻觉（Gekhman 等人，2024）。OpenAI 在 2026 年宣布逐步停止提供自助式微调，Anthropic 的 API 则从未提供过微调；请查阅最新文档。提示词不够用之后，再用微调来调整格式或语气。

### 误用知识库会引入的错误

- **过期的副本。** 被建入索引的记录相当于一个没有失效机制的缓存。
- **相互冲突的版本。** 检索同时返回了 2025 年的退款政策和已被取代的 2023 年版本，答案把两者混在了一起。
- **记录泄露。** 其他客户相似的数据行排名靠前；叫模型忽略它们并不是访问控制（OWASP Vector and Embedding Weaknesses）。
- **检索未命中。** 检索只返回了排名靠前的匹配，也就是 Amina 三次测验成绩中的两次，于是模型悄悄地对 92 和 85 求了平均，而不是对 92、78 和 85 求平均。

### 组合多种来源

真实的问题会混合多种类型，所以要把每一部分交给负责它的来源：

```text
“Python for AI 这门课能退款吗？”
政策      <- RAG：现行退款政策
报名情况  <- 实时查询：2025-09-02 报名，已完成 18%
退款资格  <- 代码：第 10 天 < 14 且 18% < 25%，所以全额退款
答案      <- 模型负责解释，引用政策，并注明截至时间
```

## 常见误区

- **“百万 token 级别的窗口意味着 RAG 已死。”** 小而稳定的资料集可以直接放进提示词；庞大、常变或有访问限制的资料集仍然需要检索。
- **“我们用政策手册给模型做微调就行。”** 微调补充事实并不可靠，没法给出引用，而且每次内容变化都要重新训练。
- **“把订单导出数据建进索引，机器人就什么都能答。”** 副本会过期，也会泄露；应该用实时查询和数据库查询。
- **“RAG 是在提问时检索的，所以内容总是最新的。”** 索引只是上一次导入时的快照。

## 典型面试题

<details>
<summary>助手什么时候该用 RAG，而不是数据库或 API？</summary>

政策文档走 RAG，过滤和聚合走数据库查询，某一个人的当前状态（比如订单状态）走实时 API 调用。规则和计算放在代码里。

</details>

<details>
<summary>长上下文和 RAG 有什么区别？什么时候你会跳过检索？</summary>

长上下文每次请求都发送所有文档，所以规模越大，成本和质量越受影响。RAG 只发送少数几个文本块，可以扩展，但可能漏掉内容。对于小而稳定、少于约 200,000 token 的语料，我会跳过检索。

</details>

<details>
<summary>客户想用他们的手册给模型做微调，你怎么回应？</summary>

微调塑造的是格式和语气，而不是知识，它既不能引用手册，也无法保持内容最新。我会建议用带引用的 RAG，把微调留给提示词解决不了的行为问题。

</details>

<details>
<summary>助手说付款失败了，计费系统却显示成功。你怎么排查？</summary>

查看这一轮记录下来的上下文：通常是一个来自已建索引的导出数据的文本块，而这份导出比计费系统的更新还旧。把记录从索引里移除，状态类问题改用带时间戳的实时查询来回答。

</details>
