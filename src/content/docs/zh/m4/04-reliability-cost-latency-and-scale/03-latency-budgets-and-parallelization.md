**一句话：** 延迟预算是一次响应允许花费的总时间，而串行的 agent、多轮调用和工具链的耗时会迅速累加，所以要用流式输出、裁剪，以及并行化相互独立的步骤来管理它，并接受并行带来的额外复杂度。

## 是什么

**延迟预算** 是约定好的功能响应时间上限（比如 3 秒以内）。LLM 系统很容易超出预算，因为工作往往是 **串行** 的：agent 调用一个工具，等待，推理，再调用下一个，再等待，每一步都会叠加自己的延迟，而多轮或多 agent 的链条会让延迟成倍放大。把延迟控制在预算之内有几个手段：**流式输出**，让用户觉得响应很快；**裁剪** 提示词和步骤；以及 **并行化** 相互独立的步骤（把彼此不依赖的工具调用同时发出）。并行化有帮助，但会带来额外的复杂度，比如要协调结果、处理部分失败，所以这是一个有意为之的取舍。

## FDE 为什么需要

一个要花 30 秒的功能，即使结果正确，也会让人觉得它坏了。FDE 要设计多步骤的 agent 系统，延迟会在其中悄悄累积，而总耗时必须控制在该应用场景能容忍的范围内。知道时间花在哪里（哪一步，串行还是可并行），并掌握压缩耗时的手段，才能让一个 AI 功能真正可用，而不只是准确。

## 核心概念

- **延迟预算：** 该应用场景的总耗时上限。
- **串行成本：** 每次工具调用、每个回合、每个 agent 都会增加延迟；链条上的延迟会累加。
- **流式输出：** 边生成边展示输出，改善感知延迟。
- **并行化相互独立的步骤：** 让互不依赖的调用同时运行，缩短实际耗时。
- **并行的代价：** 协调、部分失败和限流，这些额外的复杂度都要考虑进去。
- **按步骤衡量：** 追踪时间实际花在哪里（与可观测性相关）。

## 常见误区

- **“换个更快的模型就能解决延迟。”** 感知速度主要来自流式输出和结构设计；真实延迟则主要由多步骤链条决定。
- **“所有步骤都并行化。”** 只有相互独立的步骤才能干净地并行；并行还会增加协调和失败处理的复杂度。
- **“延迟是模型的问题。”** 它在很大程度上是架构问题，取决于你设计了多少个串行步骤和调用。

## 典型面试题

<details>
<summary>agent 系统为什么会变慢，你会怎么应对？</summary>

因为工作是串行的：每次工具调用、每个回合、每次 agent 之间的跳转都会增加延迟，链条还会让延迟成倍放大。我会设定延迟预算，用流式输出改善感知速度，裁剪不必要的步骤和上下文，把相互独立的调用并行化来缩短实际耗时，同时接受由此带来的协调复杂度。我还会按步骤衡量，看清时间实际花在了哪里。

</details>

<details>
<summary>并行化的取舍是什么？</summary>

它能缩短相互独立步骤的实际耗时，但会增加复杂度：要协调并合并结果，要处理某个分支失败导致的部分失败，还要在大量调用同时发出时不触发限流。所以我只在步骤确实相互独立、而且缩短延迟的收益值得额外处理成本时，才做并行化。

</details>
