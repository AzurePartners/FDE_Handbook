**一句话：** 一次出色的聊天回答只能证明模型有能力完成任务，不能证明它在无人看管、大批量调用、软件又对返回内容照单全收的情况下，每次都能做对。

## 是什么

在聊天里，你本身就是系统的一部分。你讲清任务，读每一条回复，觉得哪条不对就换个说法重问。应用本身也在帮忙：Anthropic 说明，Claude 的应用会“使用系统提示词来提供最新信息，比如当前日期”，而这些提示词“不适用于 Claude API”。

家庭厨师边做边尝；餐厅每晚要上 500 道菜，没人在客人之前尝过。聊天就是家里的厨房。

聊天展示的是能力：模型能够成功。系统需要的是可靠性：在无人监视、输出直接流入其他代码的情况下，每次调用都要成功。Anthropic 的评测指南把 `pass@k`（k 次尝试中至少成功一次）与 `pass^k`（k 次全部成功）作了对比。聊天演示属于 `pass@k`，因为用户会一直重试，直到结果看起来对为止。

## FDE 为什么需要

一家电信公司的客服主管把 30 张工单粘贴进聊天应用：“把每张工单标成 billing、outage、account 或 other。”30 张看起来都对，于是她让你“直接接上去”，接到一个每天约有 6,000 张工单的工单系统（数字和比率仅为示例）。在聊天里，她重新措辞过两次，还略过了两张西班牙语工单。

接到 API 上之后，日志显示零错误。可是有 2% 的回复编造出了标签（如“Billing/Refund”），落进默认队列；另有 1% 的紧急服务中断工单被判成合法但错误的“other”，所以没有人会收到告警：每天有 60 位客户被错误分流。重试过的工单会得到不同的标签，于是审计日志和队列的记录对不上。

## 核心概念

### 聊天悄悄提供了什么

API 调用只会收到你的代码发送的内容，所以应用必须自己提供：对话历史（消息角色）、指令和标签清单（提示词结构）、查询工具（tool calling），以及带兜底的输出检查（程序化 LLM 接口）。

### 静默失败看起来像成功

大多数模型失败都以正常响应的形式出现：一个错误但合法的标签、一次拒答，或者一条在 token 上限处被截断的回复（停止原因 `max_tokens`），除非代码去检查，否则都会被当作答案放行。

```python
label = next(b.text for b in resp.content if b.type == "text").strip()  # "Billing/Refund"
queue = QUEUES.get(label, "general")  # 进错了队列，也没有报错
```

OWASP 的 GenAI LLM Top 10 2026（2026 年 8 月）把这类问题归在 LLM07:2026 Misinformation 之下，称其为“系统层面的失败”：错误的输出“被信任并据此采取行动”。

### 规模会让罕见变成每天

每天 6,000 次调用，1% 的失败率意味着每月约 1,800 个糟糕的结果，而在寥寥几次聊天尝试中几乎看不出来。多步串联会让误差叠加：四个各 95% 成功的步骤，端到端只有约 81%（`0.95^4`），这是一条以各步错误相互独立为前提的经验法则。Anthropic 的 agent 指南警告会出现“错误叠加”，并建议在步骤之间加检查。

### 输出的波动会打破重试的前提

同样的输入可能返回不同的答案（机制见“生成参数”），所以重试不再等于重复，审计日志无法复现，测试也会变得不稳定（flaky）。调 temperature 解决不了问题：Anthropic 指出，即使设为 0.0，结果也“并非完全确定”，而且 Claude Opus 4.7 及之后的版本、Sonnet 5 及之后的版本以及 Fable 系列模型，会拒绝 1.0 以外的任何 temperature 值。

## 常见误区

- **“在 ChatGPT 或 Claude.ai 里能用，API 的表现就会一样。”** 聊天应用可能会加上系统提示词、记忆和工具，而且每条回复都有你来读。API 只会收到你发送的内容。
- **“它通过了 20 条测试提示词，所以是可靠的。”** 真实失败率为 1% 时，20 条提示词全部通过的概率约为 82%（`0.99^20`）。20 次零失败，在 95% 置信水平下只能说明失败率低于约 15%。
- **“换更新的模型就能解决可靠性问题。”** 新模型提升的是能力，补不上缺失的上下文。Laban 等人（ICLR 2026）发现，当任务跨越多轮对话时，平均表现下降 39%，主要原因是“不可靠性显著上升”。

## 典型面试题

<details>
<summary>为什么聊天里表现好，并不意味着 LLM 功能可靠？</summary>

在聊天里，是人在提供上下文并检查每条回复，应用还会补上提示词和工具。在系统里，输出是无人看管、大批量地流进其他代码的，所以罕见的失败会变成每天都在发生的事故，而且这些错误看起来都是合法的。

</details>

<details>
<summary>模型“能做到”一项任务与“可靠地做到”有什么区别？</summary>

“能做到”是指 k 次尝试中至少成功一次（`pass@k`），聊天演示展示的就是这个。“可靠”是指 k 次全部成功（`pass^k`）：每次成功率为 75% 时，连续三次都成功的概率只有约 42%。

</details>

<details>
<summary>客户想把在聊天里跑通的工单分诊接到他们的工单系统。你会先做什么？</summary>

先列出聊天悄悄提供了什么（指令、标签、上下文、人工检查），再让应用逐项补上，同时加上输出检查和人工兜底队列。然后在真实工单上测量错误率，与客户约定一个可接受的比率。

</details>

<details>
<summary>一个提取任务的日志里没有错误，但财务反馈发票合计金额对不上。可能是怎么回事？</summary>

是静默错误：日志记录的是异常，而不是错误但合法的值或被截断的回复。查看已存储的停止原因，抽一批样本与源文档比对，并增加检查，比如核对明细行之和是否等于总额。

</details>
