**一句话：** 端到端薄切片是指在构建其他任何东西之前，先让一个范围很窄的问题走完整个系统，从用户输入一直到最终答案。

## 是什么

Alpha 构建在 MVP 冻结之后开始。这时最容易想到的是一层一层地做：先做完数据导入，再做检索，再写提示词，最后做界面。切片的思路正好相反：你挑一个范围很窄的场景，让每一层都能处理它，哪怕处理得很粗糙。

对 Course Support Assistant（课程支持助手）来说，切片是这样的：学员输入“Data Analysis Bootcamp 的退款期限是多久？”，系统检索出退款政策那一段，模型带引用作答，答案显示在屏幕上。写死的值、只有一份文档、界面很丑，这些都没关系。

这就是 Shape Up 中“先完成一块”的思想：一块能运行的完成品，胜过许多做了一半的部件。以演示为先的思路见 [演示驱动开发](../../m5/06-demo-feedback-and-change-management/01-demo-driven-development.md)（M5）。

## FDE 为什么需要

在客户现场，一个跑不起来的系统会把所有集成问题一直藏到后期。一个团队花两周做数据导入，之后可能才发现政策 PDF 是扫描图片，解析器什么也解析不出来。切片能在第二天就把这个问题暴露出来，那时调整方向的成本还很低。它也让客户有一个真实的东西可以给出反馈。

## 核心概念

按三条规则选切片。第一，它必须经过架构图中的每一个组件。第二，它必须是客户真正在意的场景，所以选常见问题，不选冷门问题。第三，它必须小到几天之内能做完。如果你选择了工作流或 agent 设计，背后的道理见 [工作流与 agent](../../m3/15-agent-architectures/01-workflows-vs-agents.md)（M3）。切片在成熟度阶梯中的位置，见 [从演示到 MVP 到试点再到生产](../../m4/05-deployment-ci-cd-observability-and-production-readiness/04-demo-mvp-pilot-production-maturity-ladder.md)（M4）。

### 你要交付什么

把这张切片卡片复制到你的仓库里：

| 字段 | 示例 |
|---|---|
| 切片问题 | “Data Analysis Bootcamp 的退款期限是多久？” |
| 输入 | 在聊天框中输入的文本 |
| 经过的组件 | 政策加载器、检索器、提示词、模型调用、答案视图 |
| 有意打桩的部分 | 登录、其他课程、升级处理、样式 |
| 预期输出 | 正确的退款窗口期，以及它出自哪一节政策 |
| 首次端到端跑通的日期 | （填写） |

### 通过标准

- 切片能从输入一直跑到最终输出，中间没有任何手动步骤。
- 输出与卡片上的预期输出一致。
- 每个打桩的部分都写了下来，没有人会把桩误认为已完成的功能。
- 没有添加冻结的 MVP 之外的任何东西。

## 常见误区

- **“切片就是一个用完就扔的原型。”** 切片是真实系统的第一根线，后续工作是把它加粗。写一次性代码是另一种错误。
- **“我应该先把数据管道做完，因为一切都依赖它。”** 数据工作做得再完美，没有能跑通的路径，真正的问题就会被藏起来。加载一份文档，把路径跑通。
- **“薄就是质量低。”** 薄指的是范围窄。这一条路径仍然应该正确、可追溯。

## 典型面试题

<details>
<summary>为什么你在做完整功能集之前，先做一个切片？</summary>

因为它能尽早暴露集成风险。我在第二天就发现了解析器的问题，而不是第三周，而且手上有一条能运行的路径可以给客户看。路径跑通之后，我才去扩展广度。

</details>

<details>
<summary>你是怎么选择先做哪个切片的？</summary>

我选了客户最在意、又能经过每个组件的最常见问题。对 课程支持助手 来说，就是一个普通的退款政策问题，而不是边界情况。

</details>

<details>
<summary>你有意给哪些部分打了桩，又是怎么跟踪的？</summary>

我给登录、其他课程和升级处理打了桩。它们都写在切片卡片的“有意打桩的部分”一行里，所以是看得见的欠账，而不是藏起来的缺口。

</details>
