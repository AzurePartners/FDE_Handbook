**一句话：** 在可靠的 AI 功能里，模型负责模糊的语言类工作，比如理解意图、从杂乱的文本中提取事实；金额、日期这类只有一个由规则确定的正确答案的事，则交给普通代码。

## 是什么

每个 AI 功能都混合着两类工作。模糊的工作有多个可接受的答案：理解客户想要什么、从一封啰嗦的邮件里提取订单号、做摘要。规则类的工作只有一个正确答案：退款金额、截止时间、权限。这类工作属于确定性代码，它对同样的输入每次都给出同样的输出。

打个比方，在餐厅里，服务员把“来点清淡的，不要坚果，酱汁分开放”变成一张清晰的点菜单，而账单由收银系统来算。

Tool calling 把这种分工正式化了：“模型自己从不执行任何东西”（Anthropic）。它提出取值；代码负责校验、计算并强制执行规则；模型负责解释结果。

## FDE 为什么需要

设想一家网络运营商的助手在处理停机补偿。试点时把政策（每停机一天补偿一份，上限为一个月的费用）直接贴进系统提示词，让模型来计算。30 次测试对话全部通过。上线第一个月，财务发现补偿金额的舍入方式和计费系统不一致，跨越月末的停机天数被算错了，还有态度强硬的客户逼得助手承诺了超出上限的补偿。法务想起了 Moffatt v. Air Canada（2024）一案：仲裁庭裁定航空公司要为其聊天机器人给出的错误退款建议承担责任。

FDE 重新划定边界：模型负责提取账户和请求，并撰写回复。一个 `calculate_outage_credit(account_id)` 工具读取停机记录，从服务器时钟获取今天的日期，应用上限并返回金额，回复中必须原样给出这个金额。

## 核心概念

### 边界划在哪里

| 工作 | 负责方 | 原因 |
|---|---|---|
| 意图、语气、摘要 | 模型 | 好几种答案都可以 |
| 杂乱文本中的事实 | 模型提取，代码检查 | 取值仍然需要核实 |
| 计算、金额 | 代码 | 只有一个正确答案，精确到分 |
| 日期、截止时间 | 代码 | 月末、时区、服务器时钟 |
| 格式检查 | 代码 | 由模式或校验和来判定 |
| 关键业务规则 | 代码 | 提示词里的规则通常有效，但不是总有效 |
| 权限 | 代码 | 在模型之外授权 |

快速判断：如果财务、法务或合规部门能把这条规则写下来，它就该放进代码。

### 为什么“通常正确”不适用于规则

- **规模。** 示例计算：每月 1,000 笔退款，99% 的准确率意味着大约 10 笔出错。
- **可重复性。** Anthropic 的术语表写道：“即使把 temperature 设为 0，结果也不会完全确定。”
- **测试与审计。** 代码可以做单元测试，也能展示它的公式；模型算错的总额，看上去和算对的一样自信。
- **形状不等于真相。** 严格模式的 tool use（由 schema 强制的参数）保证字段和类型正确，不保证取值正确。

这并不是说“模型不会算数”：先进模型在 2025 年国际数学奥林匹克竞赛中达到了金牌水平。理由在于确定性、可审计性，以及由谁对结果负责。

### 混合方案：模型提取，代码计算

```text
客户消息    -> 模型提取 {account_ref, wants}
提取出的值  -> 代码校验、读取记录、计算
工具结果    -> 模型用通俗的话解释
回复草稿    -> 代码检查金额与工具返回的一致
```

12-Factor Agents 也这么主张：“LLM 决定做什么，但怎么做由你的代码控制。”

代码也要用对类型：在 Python 里，`0.1 + 0.2` 得到 `0.30000000000000004`，所以金额要用 `Decimal` 或整数分来计算，并采用计费系统的舍入模式。

## 常见误区

- **“模型现在很会算数，所以可以让模型算退款。”** 问题不在能力：业务计算必须能精确重复、能给出公式，并能通过测试。
- **“提示词禁止超过上限，所以上限就被强制执行了。”** 反复纠缠的用户或注入的文本可以绕过提示词里的规则。OWASP 建议在下游系统里强制授权，而不是交给模型。
- **“有了代码执行工具，模型算的数学就是确定性的。”** 沙箱是确定性的，但模型每次都会写新的代码，可能改变公式。固定的规则应该放进经过测试的工具。

## 典型面试题

<details>
<summary>把模型判断与确定性执行分开，是什么意思？</summary>

模型做模糊的语言类工作：意图、提取、摘要。凡是有唯一一个由规则定义的答案的事（金额、日期、格式、权限），都由代码来做，因为代码可重复、可测试、可审计。

</details>

<details>
<summary>由模型计算的退款，和退款工具有什么区别？</summary>

模型算出来的退款是生成的文本：通常正确，但永远没有保证。用工具的话，模型提取输入，经过测试的代码把政策应用到真实订单上，模型再转述结果。

</details>

<details>
<summary>为一个根据发票邮件安排付款的助手设计边界。</summary>

模型提取供应商、发票号、金额和到期日。代码匹配采购订单、重新计算总额、确定付款日期并检查审批额度。对不上的交给人处理。

</details>

<details>
<summary>回复里的总额和计费系统差了几分钱。你怎么修？</summary>

先在 trace 里看有没有模型自己做的算术，再在代码里查有没有用浮点数或不同的舍入规则。用 `Decimal` 并采用计费系统的舍入方式来计算，让回复直接引用工具返回的值，再补上输出检查和测试。

</details>
