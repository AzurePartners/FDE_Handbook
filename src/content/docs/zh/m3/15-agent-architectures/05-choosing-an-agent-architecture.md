**一句话：** 选择 agent 架构，就是挑出能可靠完成任务的最简单设计（从普通代码到多个 agent），并用风险、成本和可靠性方面的证据来为这个选择辩护。

## 是什么

可选的方案构成一道阶梯：普通代码；[工作流](./01-workflows-vs-agents.md)，由代码固定步骤，模型负责其中一部分；[单个 agent](./03-single-agent-systems.md)，由模型挑选每个下一步；或者[多个 agent](./04-multi-agent-systems.md)。每往上一级，灵活性就多一分，同时要付出金钱、速度、一致性和可测试性的代价。

打个比方，以人员配备为例：拿着检查清单的办事员便宜又可预测，专家能应付意外情况但需要信任，团队覆盖面更广，但每次交接都会丢失一些信息。

Anthropic 把这条规则表述为：“尽可能找到最简单的方案，只在必要时才增加复杂度。”选择要按流程来做，往往还要细到每个步骤。

## FDE 为什么需要

一家抵押贷款机构的试点用六个 agent 审查贷款档案，选它的理由是“多 agent 是现代做法”。每份档案要花约四分钟、40 次模型调用，重跑会得出不同的结论，其中一个 agent 还自己去算收入比率，而且没有人能告诉合规部门，究竟是哪个 agent 标记了某位申请人。

下面的几个问题暴露了这种不匹配：每份档案走的步骤都一样，出错代价高且受监管，文档分属约十二种已知类型。FDE 把它重建为工作流：模型负责分类和提取，经过测试的代码套用放贷规则，一个 agent 处理不常见的文档，由核贷员（underwriter）做决定。选型依据对比的是错误率、每份档案的成本和审计轨迹，从来不是方案有多先进。（示例场景。）

## 核心概念

### 决定选择的五个问题

| 问题 | 更简单的情形 | 需要更多自主性的情形 |
|---|---|---|
| 步骤能提前列出来吗？ | 每次路径相同 | 路径取决于中途的发现 |
| 错误操作的代价有多大？ | 涉及资金、申报，不可逆 | 有人审核的草稿 |
| 输入有多多样？ | 几种已知类型 | 开放式 |
| 能接受多大的延迟和成本？ | 几秒，每条几美分 | 几分钟，每个任务几美元 |
| 如何测试和审计？ | 审计员能逐条追溯的规则 | 由评测检查的结果 |

### 默认顺序，以及何时往上走一级

从可能行得通的最低一级开始。只有当你的评测集（根据[成功标准](../13-agent-profiles/06-agent-success-criteria.md)构建的测试用例）显示出一个失败，而且更高一级能修好它时，才往上走：

- **从代码到工作流：** 输入是语言类内容（邮件、扫描表单），规则无法可靠地处理。
- **从工作流到单个 agent：** 路径多变；路由越来越多，或者“其他”分支越来越大。Anthropic 建议在你“没法硬编码出固定路径”的地方使用 agent。
- **从单个 agent 到多个：** 工具和指令已经写得更清楚，它仍然选错工具（OpenAI 的判断标准）；某个子任务需要自己的安全边界（Microsoft 的标准）；或者广度并行的调研值得花约 15 倍于一次聊天的 token（Anthropic 给出的数字）。

### 写下选型依据，并回头复查

用客户的语言写一份简短的决策记录（示例）：

```text
决策：工作流，外加一个处理不常见文档的 agent
否决：六个 agent 的试点方案
风险：放贷规则放在经过测试的代码里；由核贷员决定
质量：正确率 96% 对 78%，150 份已标注档案，每份运行 3 次
成本：每份档案 5 次模型调用、20 s（试点：40 次、4 min）
审计：每一步都记录输入、输出和规则版本
复查：不常见文档超过 15%，或出现新模型
```

“更先进”不是客户能核实的理由；错误率、成本和审计轨迹才是。这份记录只是一个假设：触发条件一出现，就重跑评测。新模型就是一个触发条件：在一项浏览基准上，Anthropic 发现升级模型比把旧模型的 token 预算翻倍效果更好，所以更简单的设计也许就能通过。往下退一级，要和往上走一级一样不犹豫。

## 常见误区

- **“多 agent 更先进，所以更好。”** 它会成倍增加模型调用、交接和调试的工作量。只在单个 agent 满足不了某项需求时才用。
- **“agent 更灵活，所以是更稳妥的选择。”** 用不上的灵活性，就是你必须测试并解释的差异；对于已知的步骤，工作流更便宜，也更容易审计。
- **“架构一旦选定，就不用再动了。”** 输入、业务量和模型都会变；复查条件一出现，就重跑评测。

## 典型面试题

<details>
<summary>“最简可行架构”是什么意思？</summary>

在客户的风险、成本和延迟限制之内，在评测集上满足已约定成功标准的最低一级。“可行”要靠测量得出，而不是想当然。

</details>

<details>
<summary>支持用一个 agent 的理由，与支持用更多 agent 的理由有什么不同？</summary>

用 agent 的前提是路径会变化。用更多 agent，则需要出现这几种情况之一：工具和指令改清楚之后失败依然存在，需要一道独立的权限边界，或者并行带来的广度值得花这些 token。

</details>

<details>
<summary>一位 CEO 想像竞争对手那样，用“一个 AI agent 团队”来处理发票争议。你怎么回应？</summary>

先约定成功标准，并把步骤梳理出来。多数争议都走已知的路径，所以我会提议用工作流，只在处理例外的那一步用智能体式步骤，并在同一份评测集上展示两种设计的错误率和每单争议的成本。

</details>

<details>
<summary>新一代模型发布了。你会改架构吗？</summary>

默认不会。我会在新模型上，用现有设计和再简单一级的设计各重跑一遍评测，如果更简单的那个也能通过，就简化。

</details>
