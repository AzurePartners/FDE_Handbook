**一句话：** Web 应用的每一层运行在不同的机器上，由不同的一方控制；把安全检查或密钥放错层，是真实应用被攻破的常见原因。

## 是什么

Web 应用分层，部分原因是出于信任。浏览器和前端运行在用户自己的设备上，用户能看到并修改那里发生的一切。后端运行在公司控制的服务器上，用户无法查看或篡改。数据库存储在请求之间需要保留的数据。

“谁控制这台机器”的不同，正是“校验和密钥放在服务器上”这条规则的全部理由。只写在前端 JavaScript 里的检查只是给用户提供方便：懂技术的用户可以直接向后端发送另一个请求，绕过它。后端没有这个问题，因为用户永远看不到、也运行不了它的代码。

前端的职责是展示和交互响应。后端的职责是权威裁决：决定什么是允许的，并保管 API key 之类的密钥。数据库的职责是持久存储，并通过“这个邮箱必须唯一”之类的约束提供自己的一层保护。

## FDE 为什么需要

相当大比例的真实安全事件，归根结底都是这个错误：某项检查只存在于前端，或者某个密钥放在了任何人都能读到的地方。如果 AI 写的功能把价格计算或 API key 放进了前端 JavaScript，这就是一个迟早会被人发现的漏洞，而不是可以以后再改的风格问题。

## 核心概念

### 什么放在哪里

| 关注点 | 应放在 | 原因 |
|---|---|---|
| 布局、动画、字段即时反馈 | 前端 | 关乎用户看到什么，不需要网络往返 |
| 真正的校验，比如“价格不能为负” | 后端 | 前端那份可以被用户绕过 |
| 权限检查，比如“这个用户能不能删除这条记录” | 后端 | 只有后端知道真正发起请求的是谁 |
| API key、数据库密码 | 后端，放在环境变量里 | 浏览器可以被查看，服务器不能 |
| 长期存储、唯一性规则 | 数据库 | 重启后依然保留，即使后端代码有 bug 也能强制执行 |

### 一个具体例子

假设有个表单用来设置折扣，规则是“折扣不能超过 50%”。只在前端检查很容易被绕过，因为任何人都可以直接向后端发送带 `discount: 90` 的请求：

```python
# 后端检查：客户端无法绕过
if discount > 50:
    raise HTTPException(status_code=400, detail="Discount too high")
```

前端检查仍然值得保留，用来提供即时反馈，但它不能是唯一的检查。

## 常见误区

- **“前端把按钮藏起来，这个功能就受保护了。”** 用户仍然可以绕过按钮，直接向后端发送底层请求。
- **“前端校验就够了。”** 前端校验运行在用户控制的机器上，后端必须有对应的检查。
- **“API key 只要混淆或压缩过，放在前端代码里也没问题。”** 压缩只是让它更难读，并不是读不出来。发送到浏览器的任何值都能被提取出来。

## 典型面试题

<details>
<summary>为什么真正的输入校验应该在后端做，而不只在前端做？</summary>

前端代码运行在用户自己的设备上，可以被读取、修改或绕过。后端运行在用户无法访问的服务器上，是唯一能强制执行一条用户绕不过去的规则的层。

</details>

<details>
<summary>第三方服务的 API key 应该存放在哪里？为什么？</summary>

放在后端的环境变量里，绝不能放在前端代码里。前端代码会被发送给每个使用应用的人，谁都能读到，所以放在那里的密钥实际上等于公开。

</details>

<details>
<summary>客户的应用有一个折扣字段，只在浏览器里检查上限。风险是什么？你会怎么跟客户说？</summary>

任何人都可以绕过浏览器端的检查，直接向后端发送一个超出范围的值。保留前端检查以保证交互响应，但要在后端加上同样的检查，因为后端是用户唯一无法绕过的一层。

</details>
