**一句话：** 当另一个人只凭你的说明，就能把系统从输入跑到最终输出时，Alpha 就算通过。

## 是什么

Alpha 是第一个能在正常路径上端到端跑通的版本。检验标准不是你能不能让它跑起来，毕竟系统是你做的。检验标准是别人能不能在没有你帮忙的情况下跑起来。

对 Course Support Assistant（课程支持助手）来说：一位同事 clone 仓库，按 README 操作，提问“Data Analysis Bootcamp 的退款期限是多久？”，得到一个正确且带引用的回答。交接方面的要求见 [交接包](../../m5/07-pilot-value-handoff-and-productization/05-the-handoff-package.md)（M5）。

## FDE 为什么需要

客户不会每次出问题都打电话找你。如果只有构建者自己能运行系统，那就谈不上交付，只是一次演示。这项检查也能尽早发现遗漏的步骤，比如一个没写下来的权限申请。

## 核心概念

### 你要交付什么

一份 Alpha 签收清单，由第二个人填写：

| 检查项 | 执行人 | 结果 |
|---|---|---|
| 只按 README 完成环境搭建 | 测试人 | 通过或不通过 |
| 正常路径问题回答正确 | 测试人 | 通过或不通过 |
| 输出显示了来源 | 测试人 | 通过或不通过 |
| 记录了疑问或困惑之处 | 测试人 | 列表 |
| 运行日志中未解决的阻断问题 | 构建者 | 数量 |

### 通过标准

- 测试人在没有向构建者提问的情况下，得到了正确的最终输出。
- 测试人确实提出的每个问题，都转化为一处 README 修改。
- 运行日志显示未解决的阻断问题为零。
- 已知的缺口都列了出来，而不是藏起来。Alpha 通过并不代表系统在边界情况上是准确的，那是下一步评测要做的事。

## 常见误区

- **“Alpha 意味着系统已经很好了。”** Alpha 意味着路径能跑通。质量要在评测阶段衡量。
- **“我最了解它，自己测就行。”** 你的了解恰恰就是偏差所在。一个新人才能发现遗漏的步骤。

## 典型面试题

<details>
<summary>你怎么知道 Alpha 完成了？</summary>

一位同事只看 README 就把它跑了起来，得到了一个正确且带引用的回答。他提出的问题都写进了 README，运行日志里也没有未解决的阻断问题。

</details>

<details>
<summary>第二位测试人发现了哪些你漏掉的东西？</summary>

说出你自己实际运行中的一个真实发现，比如一个没写进文档的环境变量，或一个从没说明过的数据文件夹。关键在于，每个发现都转化成了一处文档修正。

</details>
