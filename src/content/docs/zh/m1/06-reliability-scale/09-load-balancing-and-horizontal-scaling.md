**一句话：** 当一台服务器扛不住流量时，要么把这台服务器升级得更强（垂直扩展），要么多跑几个副本、把流量分摊给它们（水平扩展），而后者需要负载均衡器。

## 是什么

垂直扩展是给单台服务器更多的 CPU、内存或磁盘。它很简单，因为应用不用改，但它有天花板，而且仍然是单点故障：这台服务器一挂，所有东西跟着一起挂。

水平扩展是运行多个服务器副本，把流量分散到它们上面。它几乎没有天花板，挂掉一台也能继续工作，但无论请求由哪个副本处理，每个副本的行为都必须一致。负责分发的是负载均衡器，它位于服务器前面，把每个请求路由到其中一台。

要让水平扩展生效，每台服务器都必须是无状态的：它不能把购物车之类的东西只存在自己的内存里，否则请求被路由到别的服务器时，就什么也找不到。无状态服务器把这类数据放在共享的地方，比如数据库或 Redis，这样任何一台服务器都能处理任何请求。

## FDE 为什么需要

一个客户系统在 10 个用户的试点中运行良好，到了 500 个用户可能就撑不住了，而原因几乎从来不是“代码太慢”。通常是这个应用压根没被设计成可以跑多个副本。如果服务器不是无状态的，“多加几台服务器”就毫无用处，因为请求可能落到一台完全没有该用户数据的服务器上。

## 核心概念

| | 垂直扩展 | 水平扩展 |
|---|---|---|
| 做法 | 换一台更大的机器 | 增加机器副本 |
| 上限 | 受限于最大的那台机器 | 实际上没有上限 |
| 故障 | 单点故障 | 挂掉一个实例也能继续工作 |
| 前提 | 无 | 应用必须是无状态的 |

```
                 +-----------+
 requests  --->  |   Load    |  ---> Server A
                 | Balancer  |  ---> Server B
                 |           |  ---> Server C
                 +-----------+
```

负载均衡器还会检查服务器的健康状况，不再把流量发给已经停止响应的服务器，所以水平扩展提升的不只是容量，还有可靠性。

**会话数据**：一个经典错误是把已登录用户的会话只存在处理其登录请求的那台服务器的内存里。下一个请求可能落到另一台从没见过这个会话的服务器上，用户就会被随机登出。把会话数据移到 Redis 这样的共享存储里就能解决。粘性会话（sticky session，把每个用户固定到一台服务器）是一种变通办法，但那台服务器一挂，会话就丢了。

如果瓶颈在别处，最常见的是数据库，那么增加应用服务器也无济于事，见“数据库瓶颈”一页。

## 常见误区

- **“加服务器总能解决慢的问题。”** 前提是应用服务器就是瓶颈，并且是无状态的。如果瓶颈在数据库，加应用服务器只会向一个已经过载的数据库发出更多请求。
- **“垂直扩展已经过时了。”** 在流量大到值得承担水平扩展的额外复杂度之前，它往往是最简单、最便宜的第一步。
- **“无状态服务器不存任何数据。”** 它的意思是不把每个请求相关的状态只保存在本地内存里。它仍然可以读写共享数据。

## 典型面试题

<details>
<summary>垂直扩展和水平扩展有什么区别？</summary>

垂直扩展是给一台服务器更多资源。水平扩展是运行多个副本，用负载均衡器分摊流量，上限更高，挂掉一个实例也能继续工作，但它要求应用是无状态的。

</details>

<details>
<summary>为什么应用服务器必须是无状态的，才能水平扩展？</summary>

负载均衡器可能把一个用户的请求发到任何一台可用的服务器。如果某台服务器把用户相关的数据只存在自己的内存里，被路由到别处的请求就找不到这些数据。把这些状态放在共享存储里，比如数据库或 Redis，就能让任何一台服务器都正确处理任何请求。

</details>

<details>
<summary>客户加了更多应用服务器，但应用还是很慢。你会检查什么？</summary>

检查数据库是不是真正的瓶颈，因为如果所有应用服务器都在等同一个过载的数据库，加多少台都没用。我会去查慢查询、缺失的索引，以及连接池的使用量与上限的对比。

</details>
