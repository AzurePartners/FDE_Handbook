**一句话：** 分支是一个指向某个提交、可以移动的指针，它为你提供一条独立的工作线，让你可以安全地修改；合并则把这个分支上的改动并回另一个分支。

## 是什么

直接在项目的主版本上工作风险很大：一个错误的改动就可能影响所有使用它的人。分支让你另开一条提交线，在上面修改、测试，准备好之后再并回来。从底层看，分支只是一个标签，指向某一个提交；在分支上每产生一个新提交，这个标签就向前移动一步，而 `main` 停在原处不动。

在 Git 里，主线通常叫 `main`。开始新工作时，你从 `main` 创建一个分支，在上面提交改动，之后再把它合并回去。合并就是把一个分支的改动并入另一个分支。大多数情况下这会自动完成；但如果两个分支以不同方式修改了同一个文件的同一些行，Git 无法判断你想要哪个版本，就会产生合并冲突，需要人来决定。

## FDE 为什么需要

客户的代码库是多人共享的，而且常常直接关系到生产环境，谁都不希望 AI 工具未经测试的改动直接落到 `main` 上。分支给了你一个安全的地方，让 AI 在里面改代码、做测试，而不会影响到其他人。如果改动有问题，删掉这个分支就行，`main` 从头到尾都没有风险。

## 核心概念

### 创建和切换分支

```
git branch new-feature        # 创建新分支
git switch new-feature          # 切换到该分支
git switch -c new-feature       # 一步完成创建和切换
```

`git checkout` 和 `git checkout -b` 是旧的写法。

### 合并

```
git switch main
git merge new-feature
```

如果两个分支改动的是不同且不相邻的行，Git 会自动合并，并生成一个合并提交。如果从分支分出去以后 `main` 上没有新的提交，Git 只是把 `main` 直接移动到分支的最新提交（称为“快进”，fast-forward），不会生成合并提交。如果两边改动的是相同或相邻的行，Git 会停下来，并在文件中加上冲突标记：

```
<<<<<<< HEAD
old_price = price * 1.0
=======
old_price = price * 1.08
>>>>>>> new-feature
```

`<<<<<<< HEAD` 和 `=======` 之间是你当前分支上的内容，`=======` 和 `>>>>>>> new-feature` 之间是要合并进来的改动。编辑文件，保留正确的版本，删掉这些标记，暂存文件，然后提交，合并就完成了。

### 决定保留哪一边

冲突不是 Git 能替你解决的，因为它根本不知道哪个值才对。你要读懂两个版本，判断哪个符合当前的意图（比如一个已修正的税率、一个已更正的默认值）。有时正确答案是把两边结合起来，而不是简单地选一边。

## 常见误区

- **“合并总是自动完成的。”** 只有改动不重叠时才会自动完成。两个分支修改了同一些行时，Git 需要人来解决冲突。
- **“出现合并冲突说明有人做错了。”** 它只说明两个人改了同一些行。这是并行开发的正常结果，不代表有人犯错。
- **“合并后删除分支会丢失工作。”** 合并之后，分支上的提交会保留在目标分支的历史里。删除分支指针只是去掉一个已经用不着的标签。

## 典型面试题

<details>
<summary>什么是合并冲突？如何解决？</summary>

当两个分支以不同方式修改了同一个文件的同一些行，Git 无法决定保留哪个版本时，就会发生合并冲突。Git 会用 `<<<<<<<`、`=======` 和 `>>>>>>>` 标记出冲突的部分。你编辑文件保留正确的内容，删除这些标记，暂存后再提交即可。

</details>

<details>
<summary>为什么要用分支，而不是直接提交到 main？</summary>

分支把你的改动隔离开，让 `main` 在你工作期间始终保持稳定、可部署。即使你的改动弄坏了什么，`main` 也不受影响，其他人可以继续在一个已知可用的状态上工作。

</details>

<details>
<summary>两位同事在各自的分支上修改了同一个函数，第二个人合并时会发生什么？</summary>

Git 会先尝试自动合并。如果两处修改落在不同且不相邻的行上，合并会自动成功；如果改的是相同或相邻的行，Git 会停下来并在文件中标记冲突，第二个人需要手动解决冲突后才能完成合并。

</details>
