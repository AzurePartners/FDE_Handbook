**一句话：** 调用外部 API 失败时，状态码和错误信息会告诉你问题属于四类中的哪一类：认证、网络、数据格式或业务逻辑。

## 是什么

集成“失败”的方式有很多种，怎么修完全取决于是哪一种。缺少 API key、网络慢、请求体格式错误，以及一条合理的业务规则（比如“不能预订过去的日期”），从外面看都差不多：你的应用显示一个错误。但它们不是同一个问题，一视同仁只会浪费时间。

首先要看的信号是 HTTP 状态码。4xx 表示客户端做了服务器不接受的事。5xx 表示服务器出了问题，往往与你的应用做了什么无关。还有一个单独的类别是超时，表示在你允许的时间内根本没有收到响应。

举个具体例子：用 Open-Meteo 的地理编码搜索查一个编造的城市名：

```
curl "https://geocoding-api.open-meteo.com/v1/search?name=Notarealplacexyz&count=1"
```

这个请求返回 200 状态码，响应里完全没有 `results` 字段，而不是返回错误。这是一个业务逻辑结果：这个城市确实不存在，并不是技术故障。它应该由应用自己的逻辑来处理，而不是写进“集成坏了”的故障报告。

## FDE 为什么需要

客户会说“集成坏了”，并期待你快速、准确地给出诊断，而不是靠猜。把认证失败和网络失败搞混，会让你走错方向，比如真正的问题是客户的防火墙，你却去轮换一个完全正常的 API key。能快速、准确地指出是哪一层出了问题，是这个岗位最能体现能力的信号之一。

## 核心概念

### 四类问题

| 类别 | 含义 | 典型信号 |
|---|---|---|
| 认证或授权 | 调用方的身份或权限不对 | 401 或 403 |
| 网络 | 请求没到达服务器，或响应没能返回 | 超时、连接被拒绝、DNS 解析失败 |
| 格式 | 请求或响应的结构与预期不符 | 400 或 422，或解析错误 |
| 业务逻辑 | 技术上成功了，但系统规则拒绝了该操作 | 404、409，或带错误字段的 200 |

有两种信号不属于这四类，下表单独标出：429 是限流（你发得太多、太快）；500、502 和 503 是对方系统的服务器端故障，问题不在你的请求。

### 状态码排查表

| 状态码 | 含义 | 类别 | 检查什么 |
|---|---|---|---|
| 400 | Bad Request | 格式 | JSON 是否合法、必填字段是否齐全、类型是否正确 |
| 401 | Unauthorized | 认证 | key 或 token 是否缺失、过期、格式错误 |
| 403 | Forbidden | 授权 | 凭证有效，但缺少权限 |
| 404 | Not Found | 业务逻辑或格式 | URL 是否正确，资源或 ID 是否真的存在 |
| 409 | Conflict | 业务逻辑 | 操作与当前状态冲突，比如记录重复 |
| 422 | Unprocessable Entity | 格式 | JSON 合法但未通过校验，比如邮箱格式错误 |
| 429 | Too Many Requests | 限流 | 超出调用量上限，查看 `Retry-After` header |
| 500 | Internal Server Error | 服务器端，不是你的问题 | 对方系统有 bug 或崩溃了 |
| 502 | Bad Gateway | 网络，服务器端 | 代理没能从 API 拿到有效响应 |
| 503 | Service Unavailable | 服务器端 | 服务过载或正在停机维护 |
| 504 | Gateway Timeout | 网络 | 代理等待响应超时，放弃了 |

每个状态码的完整定义在状态码那一页；这张表专门讲集成出故障时，每个状态码指向哪一类问题。

### 按顺序排查

一个实用的检查顺序，最快、最常见的排在前面：先确认请求到达了服务器（网络），再确认凭证有效且有权限（认证与授权），然后确认请求和响应的结构对得上（格式），最后才假定是系统按自己的规则正确地拒绝了该操作（业务逻辑）。还没看实际的错误响应体就直接“轮换 key”，只会浪费时间。

## 常见误区

- **“只要报错就说明 API 坏了”以及“超时和 500 是同一个问题”。** 这两点都在 [错误响应与超时](./03-error-responses-and-timeouts.md) 中讲过。
- **“返回 200 就说明集成没问题。”** 结果字段为空或缺失的 200，比如上面的地理编码例子，仍然可能是你的应用必须处理的业务逻辑结果。
- **“401 和 403 可以互换。”** 401 表示服务器不知道你是谁。403 表示服务器很清楚你是谁，并且决定你不能做这件事。遇到 401 查凭证，遇到 403 查权限。

## 典型面试题

<details>
<summary>客户的集成返回了 403。你先检查什么？为什么不是 API key 本身？</summary>

检查凭证的权限和 scope，而不是它是否存在。403 表示服务器已经识别出调用方，并根据它被允许做的事拒绝了这个操作；这和 key 缺失或无效是不同的问题，那种情况会返回 401。

</details>

<details>
<summary>怎么判断一个失败是网络问题还是业务逻辑问题？</summary>

网络问题表现为超时、连接错误，或代理返回的 502、504：请求始终没有从目标服务拿到真正的回复。业务逻辑问题会收到正常的响应，通常是 200、404 或 409，说明服务理解了请求，并告诉你这个操作不合法。

</details>

<details>
<summary>客户坚持说“集成坏了”，但 API 返回的是 200 和一个空结果。你怎么回应？</summary>

解释清楚：响应体为空或携带错误信息的 200，是一次成功的技术响应，描述的是一个业务结果，而不是集成本身出了故障，比如一次确实什么都没搜到的搜索。在认定系统有问题之前，先和客户一起过一遍这个请求实际查的是什么。

</details>
