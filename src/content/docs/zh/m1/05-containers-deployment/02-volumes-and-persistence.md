**一句话：** 容器自身的文件系统会随着容器被替换而消失，所以任何需要保留下来的东西，比如数据库或用户上传的文件，都必须放在容器之外的地方。

## 是什么

设想一个小应用把搜索历史存在容器自身文件系统里的一个 SQLite 文件中。在本地这样做看起来没问题：只要应用一直在跑，文件就一直在。但云平台“重启”应用，通常是启动一个新容器。每当平台替换容器（重新部署、扩缩容、宿主机维护），写在旧容器自身磁盘上的东西就全没了。历史记录丢了，不是因为哪里坏了，而是应用把数据放错了地方。

这背后的理念是 **无状态进程**，出自 Twelve-Factor App，一套被广泛引用的云软件实践。进程应当被视为随时可能被停止和重启，它需要的任何东西都不应只存在于进程内部。需要持久保存的数据应该放在 **支撑服务**（backing service）里：数据库、文件存储服务、缓存，或者应用通过网络连接的其他资源。

**卷**（volume）是挂载到容器上的、位于容器之外的目录，写到这里的文件在同一台机器上重启后依然存在。本地开发时它很有用，但在云上通常不够，因为平台经常在不同的宿主机上替换容器。正确的做法是使用托管的支撑服务，比如云数据库，它不依赖任何一个具体的容器。

## FDE 为什么需要

这是新 FDE 常会碰到的一个意外故障：演示一切正常，部署上线，然后一次例行重启悄无声息地清掉了大家以为很安全的数据。理解其中原因，决定了你是对着“数据丢了”手忙脚乱，还是冷静地解释：解决办法是改用支撑服务。客户投诉“数据丢了”，很多时候实际问题出在状态存放的位置上。

## 核心概念

### 无状态进程

如果一个进程下次运行时，不依赖任何保存在自己本地磁盘上的东西就能正确工作，它就是无状态的。它可以被停止、替换，或者扩展成多个副本，行为都不会改变。

### 支撑服务

支撑服务是应用通过网络访问的任何资源：数据库、缓存、文件存储桶，或外部 API。Twelve-Factor App 把它们看作附加资源，无需改动应用代码就能替换，例如只改一个连接字符串，就能让应用指向另一个数据库。

## 常见误区

- **“Docker 卷和托管数据库解决这个问题的效果一样。”** 卷能保证本地开发时某个本地目录不被清空，但在大多数云平台上，它无法可靠地挺过重新部署或扩缩容。
- **“应用重启了，说明肯定有东西坏了。”** 重启是常规操作。只有当应用假设本地状态能挺过重启时，才会出问题。
- **“无状态意味着应用不能有任何数据。”** 意思是进程本身不应是数据唯一的存放处；数据应该放在支撑服务里。

## 典型面试题

<details>
<summary>为什么容器的本地数据在重启后会消失？</summary>

新容器从镜像的一份干净副本启动，而云平台会例行替换容器。写到容器自身文件系统里的东西只存在于这个容器的可写层中，容器被删除时一并丢弃，除非它写到了卷或外部服务里。

</details>

<details>
<summary>什么是支撑服务？请举一个例子。</summary>

应用通过网络连接的资源，可以替换，而不是内置在应用里。托管数据库就是一个例子；文件存储桶或外部 API 也是。

</details>

<details>
<summary>一个应用把数据存在自身容器内的 SQLite 文件里，每次部署都会丢数据。你会怎么建议？</summary>

把数据迁到专门用于持久保存的支撑服务里，比如托管数据库。应用进程应该保持可替换，因此任何重要的东西都不应依赖于在容器内部存活下来。

</details>
